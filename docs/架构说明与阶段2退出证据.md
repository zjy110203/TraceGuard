# 阶段 2 执行内核：架构说明与退出证据

> 本文记录 v1.1「阶段 2：专业 Web UI 自动化测试框架」的可运行落地。
> 设计依据：`实施线路/TraceGuard-完整项目实施路线图-v1.1.md` 第 411–505 行。
> 前置：M0/M1 工程骨架与 TeamFlow（见 `架构说明与M0-M1退出证据.md`）。
> 纪律：只实现本轮**已冻结**的规则；P01/P03/RV-01/04 保持待确认，不冒充已裁决。

## 1. 最小闭环是什么

先区分两个容易混淆的词：

- **地基（M0/M1，已完成）**：被测应用 + 五类故障注入 + Ground Truth 隔离。它是一个"可复现的考场"。
- **最小闭环（阶段 2，本文）**：加载用例 → Playwright 执行 → **自动采集观察** → Oracle 判定 → Verdict 聚合 → Run/Step 报告。

`TestCase → 执行 → 观察留证 → 比对诊断 → 报告`，这是 TraceGuard 第一次真正"做完一件它该做的事"。所有后续功能（Explorer、Compiler、诊断、自愈）都将挂到这条链路上迭代，而不是先补齐 14 阶段图纸。

## 2. 先钉死哪个部件

**Verdict 聚合器**——全场唯一"已冻结、不依赖任何待确认项"的部件。它是纯函数，无 Playwright/DB/Agent 依赖，可用表驱动测试穷举。路线图第 467 行明确写了护栏：

> 在 Oracle 多来源细则（P03）确认前，无法裁决的冲突一律按 INCONCLUSIVE 处理，**不得擅自设定 Primary Oracle 覆盖 Supporting Oracle**。

因此 `evaluate_oracle_binding` 与 `OracleEvaluator._aggregate` 都实现"分歧→INCONCLUSIVE"，没有任何 Primary 优先策略。

## 3. 冻结的 Verdict 规则（`packages/execution/verdict.py`）

| 条件 | Test Verdict |
|---|---|
| 至少一个必需 Assertion 明确失败 | FAILED |
| 所有必需 Assertion 通过、执行正常、Oracle 有效 | PASSED |
| 无明确失败，但部分必需 Assertion 无法裁决 | INCONCLUSIVE |
| 没有任何必需 Assertion 得到有效评估 | NOT_EVALUATED |

关键边界（都用测试钉死了）：

- **空必需集合非法**：不允许靠空集合逻辑自动 PASSED（raise `InvalidTestCaseError`）。
- **"有效评估"的精确定义**：断言真跑了 + Oracle 可读 + 结论不是 NOT_EVALUATED。INCONCLUSIVE 属于"评估过但裁不了"，仍算有效评估——否则唯一的必需断言一冲突就掉进 NOT_EVALUATED，违背规则"冲突→INCONCLUSIVE"。
- **Oracle 不可用不 PASSED**；`execution_completed=False` 时也不 PASSED（防止"清理阶段崩溃却被判通过"）。
- **四维度独立**：`execution_status` / `test_verdict` / `diagnosis_status` / `diagnosis_outcome` 各有字段，不由一方推导另一方。诊断两字段本阶段固定 `NOT_STARTED`（属阶段 7）。

## 4. Oracle 与观察的可信边界

这是整个设计最需要想清楚的信任问题：**如果被测应用自己就能改 Oracle，诊断就没有意义。**

- Oracle 只读两类可观察事实：业务面独立状态 API（`state.*`）和浏览器 UI 观察（`ui.*`）。
- **绝不读** `/__eval__` 控制面、Ground Truth 或故障配置——Agent 和业务面都拿不到答案。
- `OracleSpec.expected_value` 是人工批准的期望值；runner 在**步骤执行之后**自动读真实状态比对（不是外部注入，否则 Oracle 不可信）。
- 多源分歧（Primary 说 PASSED、Supporting 说 FAILED）→ INCONCLUSIVE 且 `oracle_conflict=True`，留给阶段 7 诊断。

### 5.2 端到端闭环（真 Playwright 驱动真 Chrome → 真 TeamFlow）

| 场景 | execution_status | test_verdict | 关键观察 |
|---|---|---|---|
| 正常创建项目 | COMPLETED | **PASSED** | 独立 API `project_count=1`，与 Oracle 一致 |
| 注入 TF-DB-001 | COMPLETED | **FAILED** | `project_count=0`，项目确实没建成 |
| 注入 TF-UI-001 | COMPLETED | **PASSED** | DB 有项目（verdict 正确），但 s9"成功消息可见"断言失败——UI 撒谎被**如实记录**为分歧，供阶段 7 诊断 |

一个值得注意的正确行为：**TF-UI-001 下 verdict 仍是 PASSED**。因为测试问的是"测试是否符合预期"——项目确实创建了，UI 藏起成功消息不该把它变成 FAIL。但 UI 与独立状态的分歧被完整捕获（step 失败 + 事件）。这正是诊断层将来要吃的信号，而不是在这里误判。

### 5.3 独立可执行性与不可变性

- `python -m scripts.run_case benchmark/cases/TC_E2E_001.json --reset`：脱离 Agent/异步平台独立执行，退出码 0，Verdict=PASSED。
- 每个 Run 生成独立报告文件，绑定具体 `case_version`；两次运行不覆盖历史（E2E 测试 `test_history_runs_not_overwritten` 验证）。
- `TestCaseVersion` 是 frozen dataclass，仓库只有 `add_version` 无 `update`——append-only 是**结构性**保证，不靠自觉。
- 每条 Run 采到 19 条证据（截图含 sha256 完整性 + DOM 快照 + 网络响应）、29 个事件（含 occurred_at/recorded_at 分离、幂等键、生产者实例内序号）。

## 6. 测试中发现并修复的缺陷（过程证据）

1. **Verdict "有效评估"定义错误**：原实现要求结论必须是 PASSED/FAILED 才算有效评估，导致"唯一必需断言 Oracle 冲突"被误判 NOT_EVALUATED，违背"冲突→INCONCLUSIVE"冻结规则。表驱动测试 `unresolved-oracle-conflict` 样例抓到，按路线图第 464 行修正定义并加显式防线。
2. **观察值外部注入的信任漏洞**：初版 runner 允许调用方注入 observation，会让 Oracle 可被操纵。重构为 runner 在步骤后**自动**从独立 API + 浏览器采集，移除注入参数。
3. **Playwright API 变更**：新版无 `SyncPlaywrightContextManager` 导出、`start()/stop()` 改为 `__enter__/__exit__`，按实际类型修正生命周期管理。
4. **logger 调用方式错误**：`logger.info("msg", path=...)` 是 structlog 风格，项目用的是标准库 logger，触发 `TypeError`。修正为标准格式（仅在写报告时触发，无 report_dir 的前 3 个测试未暴露）。
5. **mypy tuple/list 不符**：`StepExecution.evidence_ids` 声明为 tuple 但传入 list 字面量，已改 tuple。

另：进程残留导致端口占用返回 500，用独立端口 + 测试内线程化 uvicorn fixture 解决（非代码缺陷，属验证环境治理）。

## 7. 未覆盖 / 明确不做（不冒充完成）

- **明确不做**（路线图 489–490）：不建 Celery 分布式调度；不引入 Browser Use；不让 Agent 决定测试结果；不原地覆盖 TestCaseVersion。
- 契约 C01–C04 仅有领域模型与标注"illustrative"的 Event/Evidence 结构；**正式 JSON Schema 仍待逐项冻结**，未编造。
- 用例规模为 1 条（覆盖正常/DB/UI 三场景），未达验收标准的 10–20 条——这是"最小闭环"，批量用例可按同一 TestCaseVersion 结构扩充。
- 诊断（阶段 7）、Compiler/Explorer（阶段 5/6）、异步平台化（阶段 3）均未实现；`diagnosis_*` 字段固定 NOT_STARTED。
- P01/P03/RV-01/04 保持待确认；Playwright/pytest 版本为本地实测解析值，未冒充团队冻结。
