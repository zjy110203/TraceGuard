# R5-5.4 故障恢复与并发验收说明

范围：单进程线程并发、真实 Python 子进程退出；不是多进程并发写入或机器断电测试。

## Candidate 故障点

| 阶段 | 真实退出方式 | 恢复后要求 |
|---|---|---|
| PREPARED | 子进程 os._exit(73) | 无正式文件/Intent，仍待审核 |
| INTENT_DURABLE | 同上 | 仅按已持久化审核决定恢复 |
| FORMAL_TEMP_DURABLE | 同上 | 隐藏临时文件不加载，恢复正式文件 |
| FORMAL_REPLACED | 同上 | 校验字节/owner 后恢复 Candidate |
| FORMAL_CASE_DURABLE | 同上 | 不能认领其他事务文件 |
| BEFORE_CANDIDATE_STATE | 同上 | 原审核信息与目标终态一致 |
| CANDIDATE_TEMP_DURABLE | 同上 | 原 Candidate 仍为完整 JSON |
| CANDIDATE_REPLACED | 同上 | 新 Candidate 完整，后续恢复幂等 |
| CANDIDATE_STATE_DURABLE / BEFORE_DONE / DONE | 同上 | DONE 核验、不重复文件/审核 |

每个适用案例还在恢复过程中再次 os._exit，之后在新进程连续恢复两次。核对正式文件数、SHA-256、transaction_id、审核人/记录、checklist、uncertainty 与完整 Candidate 快照。27 项新专项包含五类文件/Intent 损坏、全部审核字段不一致、正常异常时原子写入保留旧 JSON、应用 lifespan 自动恢复和 Intent 预留。

原 f68de9b 源码单独载入隔离进程后，在正式文件写入后、Candidate 保存前 os._exit(74)，实际复现正式文件存在且 Candidate=PENDING_REVIEW。基线代码与正式用户数据均未改动。

## 并发覆盖

| 操作 | 实际方法 | 断言 |
|---|---|---|
| approve + approve | 两线程同步起跑 HTTP POST | 200+409；一个有效事务/正式文件 |
| approve + reject | 同上 | 200+409；仅一个终态 |
| reject + reject | 同上 | 200+409；一个拒绝审核快照 |
| compile + compile | 八线程同步起跑 HTTP POST | 同一个候选/标题，无覆盖 |
| approve + compile | 两线程同步起跑 HTTP POST | 最终批准状态保持，源关系不变 |

另验证不同 Candidate 不能占用已持久化 Intent 预留的 Case ID。使用的是共享应用的真实路由与并发 handler，不是顺序调用 Service 冒充并发。

SSE 的历史全量失败日志保留；修复测试读取旧订阅基数的时序问题后，原模块 7 项通过，并新增结束后订阅清理断言。Repair 原有并发/CAS/os._exit/恢复专项均保留，由最终全量和 Security 门禁重跑。
