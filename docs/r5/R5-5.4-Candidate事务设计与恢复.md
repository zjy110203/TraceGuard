# R5-5.4 Candidate 事务设计与恢复

状态：已实现；完整门禁以本轮验收报告为准。范围：Windows 本机、单用户、loopback、单进程、单 Worker。

## 审计结论与实现

基线 f68de9b 的 CandidateStore.save 和正式 Case 使用直接 write_text。approve 的 Case 写入与 Candidate 更新之间没有恢复协议；approve/reject 与 compile 的读改写没有统一 Candidate 锁。

本轮统一锁顺序为 CandidateStore 目录 + candidate_id 的进程内 RLock → 正式 Case 目录 + case_id 的 RLock。compile 的查重和保存也在 Candidate 锁内。不同候选争用同一 Case 时由正式 Case 锁、持久化 Intent 预留与文件存在检查保护。不是跨进程锁。

原子写入使用目标同目录 mkstemp → 完整 UTF-8 JSON → flush → fsync → os.replace。正常异常时清理临时文件；进程直接退出留下的隐藏 .tmp 不作为正式文件加载。不会先删除目标。保证测试覆盖的进程退出场景中读到完整旧/新文件，不承诺机器断电级持久性。

## 状态机

PREPARED（仅内存）→ INTENT_DURABLE → FORMAL_CASE_DURABLE → CANDIDATE_STATE_DURABLE → DONE。任意所有权、摘要、Candidate 快照冲突 → BLOCKED，保留文件。

transactions/cand_*.json 保存唯一 transaction_id、candidate/case、操作、原/目标状态、源 Trace hash、正式 Case 完整内容及字节 SHA-256、前后 Candidate 快照与摘要、reviewer、approval_record、review_confirmed、uncertainty_acknowledged、时间、阶段。拒绝也走相同协议，没有正式 Case 载荷。

正式文件仅增加存储 envelope `_candidate_transaction`，严格 loader 与既有 `_repair_transaction` 一样剥离该字段；不修改活动 TestCase schema，也不覆盖历史版本。

## 恢复

应用 lifespan 自动恢复；审核/编译/详情读取前对指定 Candidate 再核验。只完成已经通过原有服务端来源、人工审核字段、checklist、uncertainty 与 Compiler 门禁并落盘的决定。Intent 前退出不产生任何批准。现有正式文件必须逐字节匹配 Intent（含事务所有权）；缺失已持久化文件、状态冲突均 BLOCKED。无归属的预存正式文件保留并记录 BLOCKED。

DONE 重复恢复不改写正式文件或追加审核。BLOCKED 不自动解除；维护者须先保全所有文件并调查。启动恢复异常显示在 health.candidate_recovery 并记录日志。自由文本审核人仍是本机审计字段，不代表身份认证。

## 验证

`tests/test_candidate_transactions.py` 用真实并发 HTTP 覆盖 approve/approve、approve/reject、reject/reject、compile/compile、compile/approve；独立 Python 子进程 os._exit(73) 覆盖 Intent 前后、正式临时文件 fsync 后、replace 后、Candidate 写入前、临时文件后、replace 后、状态阶段后、DONE 前/后。恢复时再次退出并两次重复恢复；比较状态、审核记录、正式文件 SHA-256 和文件数。故意修改文件内容、owner、Candidate、Intent 或丢失正式文件必须保留并阻断。原有 Candidate 测试不删除、不降低断言。

自动化测试中的 reviewer 是隔离测试输入，不构成真实项目方人工批准。

基线原始源码真实进程退出复现：exit=74、正式文件存在、Candidate=PENDING_REVIEW；reproduction.json 保留复现结论。该测试未动正式用户数据。新版事务专项额外覆盖应用 lifespan 恢复及 Intent 后写失败时其他 Candidate 不得占用 Case ID。
