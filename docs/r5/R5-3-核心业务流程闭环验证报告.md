## 2. 为什么必须新增全链接口（而不是只补页面）

审计发现：**执行与证据面是断开的**。`POST /tasks/{id}/runs` 会写 `tg_run` / `tg_step`，但从不写 `ev_event` / `evd_record` / `gr_node` / `gr_edge`；唯一会产出证据与图谱的代码是 `scripts/run_benchmark.py`，它不可从产品访问。

后果：证据台账、证据图谱、诊断三张页面在正常使用下**永远只能显示空态**。这不是前端缺陷，是后端能力缺失。

因此本轮新增 `apps/api/chain_api.py`，直接复用 `packages.execution.pipeline.FullChain`（benchmark 脚本用的同一份代码），并把产出落到证据面：

```
TestCaseVersion → LocalRunner（真实 Chrome）
  → Verdict → EventStore.append（17 事件/次）
  → EvidenceManager.import_record（9~11 证据/次）
  → CorrelationGraph（节点/边）
  → DiagnosisService
  → RunService（合法状态机注册，成为一等 Run）
```

### 2.1 关键设计取舍

| 问题 | 取舍 | 理由 |
|------|------|------|
| 证据哈希怎么算 | `import_record` **保留 runner 已算的 `integrity_check`**，不重新哈希 | `add_raw` 会对「记录的 JSON 视图」算哈希，得到的摘要不描述真实抓取物，等于伪造完整性 |
| 截图二进制放哪 | hex 解码后进 `LocalBlobStore`（内容寻址），DB 只留引用 | 一次 10 步用例的 base64 会撑到 MB 级，污染证据表 |
| 链路执行要不要注入 fault/probe | **都不注入** | probe 需要 handler 桩，桩的返回值不是证据；fault 由评测面提供，产品端点无从获取 |
| 失败执行怎么处理 | 201 + `completed=false` + 失败明细入 stage | 执行失败是真实结果，不是服务器错误 |
| 谁能执行 | `approved_by` 为空 → 409 | 未经人工评审的候选不得通过产品端点执行 |
| 链路 Run 的注册 | 走 `RunService` 合法状态转换 | 直接插终态行会被状态机拒绝，也不能伪造历史 |

## 3. 候选评审门禁（Candidate → TestCase）

`apps/api/candidate_api.py` 落实三条不变式，并有测试固定：

1. **编译不产正式资产**：`compile` 只写候选 JSON；`GET /api/v1/cases` 在批准前保持为空（`test_compiled_candidate_is_not_written_to_case_library`）。
2. **批准必须可追溯**：`reviewer` 与 `approval_record` 缺一 → 422；批准时才把 Oracle 置为 `approved=true` 并记录批准人（编译器初始 `approved=false`，这是它自己的守卫）。
3. **评审结论不可被重编译抹掉**：同一轨迹重复编译，`PENDING` 幂等返回；已 `APPROVED`/`REJECTED` 则 409（`test_recompile_after_review_is_refused`）。

## 4. 本轮发现并修复的真实缺陷

均为**真实运行/几何测量/截图审阅**暴露，非代码走读猜测：

### 4.1 全链路不加载逻辑定位符（严重）

首次真实全链运行 `TC-LOGIN-001` 判为 `FAILED`，`s2~s5` 全失败。DOM 快照证据显示登录页正常渲染（`TeamFlow | 用户名 密码 登录`），排除目标应用问题。
根因：`FullChain.__init__` 构造 `LocalRunner(self.base_url)` 时**未传 `locators`**，`loc:login.username` 被当作字面 CSS 选择器送进 Playwright。
修复：`FullChain` 增加 `locators` 参数并下传；`chain_api` 传入编排器的同一份 `LocatorRegistry`；`scripts/run_benchmark.py` 同步。修复后同一用例 `PASSED`、11 证据。

### 4.2 `chain_id` 校验拒绝含连字符的用例 ID

首次调用返回 422：`invalid chain id: chain_20261123055634601168_TC-LOGIN-001`。
根因：落盘路径校验正则 `chain_[A-Za-z0-9_]+` 未覆盖用例 ID 的 `-`（该 ID 由 `scenario_id` 拼接而来）。
修复：允许 `-`，仍禁止 `.` 与路径分隔符（路径穿越测试保留）。

### 4.3 编译出的用例永远无法判定

编译候选的 Oracle 绑定到 `ui.s4.passed`（探索动作的最后一步点击），而 runner 只对 `assert_*` 步骤写入 UI 观测 → Oracle 恒 `UNAVAILABLE` → verdict 恒 `NOT_EVALUATED`。
修复：runner 对**每个步骤**发布 `ui.<step>.passed`。语义保持不变且更窄：它的含义正是编译器声明验证的「探索过的动作仍可成功执行」，不是新增业务断言。既有 12 个 oracle 全部指向 `assert_*`，故无行为变化。

### 4.4 重新编译会静默覆盖评审结论

候选 ID 由轨迹哈希派生，同一轨迹重编译命中同一文件。原实现直接覆写，会把 `REJECTED`（含退回理由）或 `APPROVED` 变回 `PENDING_REVIEW`。
修复：`PENDING` 幂等返回；已评审返回 409 并保留原因。

### 4.5 图谱节点点击被拖动手势吞掉

验收断言 `graph node click shows detail panel` FAIL。根因：`pointerdown` 即 `setPointerCapture`，后续派生 click 被重定向到 `<svg>`，节点上的 `@click.stop` 永不触发。
修复：按压起点落在节点上则不平移；平移需超过 4px 阈值才生效；`pointerup/cancel/leave` 统一收尾。同时给节点加 `data-node-id` 稳定钩子。

### 4.6 有数据后 Runs 页在 390px 溢出

空表时期验收全绿，接入真实数据后 `documentElement.scrollWidth=417 > 390`。几何测量定位到 `LABEL.inline-label`（宽 403）——其内 `<select>` 被最长的 Task ID 选项撑开。
修复：`.inline-label` 与其中控件加 `min-width:0; max-width:100%`（全局，受益于所有含下拉筛选的页面）。复测 `scrollWidth=390`。

### 4.7 图谱视觉：标签重叠/裁切、边表被挤压

截图审阅发现：20 节点圆环上标签互相压叠、左右两侧被 viewBox 裁切；右侧 4 列边表把 `dst`/`rule` 挤出面板。
修复：标签沿半径向外排布 + 中段省略（保留尾部特征，`run_2…140137:Run`）+ 文字描边光晕；画布 640→760 并重算半径；边明细改为行式列表（关系徽章 + `src → dst` 单行省略 + 规则号）；图谱栏在 ≥1100px 时占 1.5 份宽度。

### 4.8 验证脚本自身被宿主安全删除拦截

`verify_all.py` 每次运行先 `unlink()` 旧的 `isolated.db`，被宿主 safe-delete 守卫拒绝（trash 失败）导致整轮验证在第一步就崩。
修复：隔离库改为按时间戳唯一命名，**不删除**（与 pytest basetemp 同一策略）。
