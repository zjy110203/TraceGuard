# R5-5.4 场景路径 Oracle 版本化修正提案

状态：本次对话用户已明确批准“批准新增版本，保留旧版不变”；已实现显式选择的 2.1.0。旧版（五个 2.0.0、form-validation 1.0.0）、正式 Oracle 与 required assertions 保持不变。以下保留发现和提案，再追加实现结果。

## 实际发现

本轮对真实 Chromium API 测试落盘的 25 次路径执行（24 个组合 + form-validation 重复 normal）重新核验 Trace hash、Scenario digest、PathSpec、required expect 与 TestCaseVerdict。25/25 来源完整性核验通过，14 次 PASSED、11 次 FAILED。既有 Python 测试检查目标/页面/清理成功，但这些断言不足以证明每条路径 TestCaseVerdict 为 PASSED。

源码原因：Scenario.path_spec_for_path 的兼容适配把所有 exception/boundary 默认写为 NOT_VERIFIED + login-error，而 project-create/query/navigation/edit 和 form-validation 的错误页面并不一定是登录错误；成功 boundary 也不是负向目标。form-validation Recovery 的全局 goal_definition 仍要求 form-error，而恢复成功后已经跳到成功列表；调用方测试输入 target=/projects/new 与 duplicate error 文本也不适用于恢复成功。

## 修正提案（不原地变更历史）

发布显式选择的新 Scenario 版本，旧 2.0.0 的 digest、路径、已生成 Case 和 Trace 保持不变。建议分两阶段：先批准各路径期望与证据；再批准路径级 goal_definition/intent_templates 的契约扩展，随后实施和回归。不得通过移除 required assertion 或把现有 FAILED 改成任意预期来绿化。

| 场景/路径 | 应核验的业务行为 | 所需独立证据 |
|---|---|---|
| project-create exception | 重复名称拒绝，未创建新项目 | form-error + 明确重复名称错误 + owned data 数量不增加 |
| project-create boundary | 200 字符名称可创建 | success-message + 列表中精确目标 + 后端 owned resource 结果 |
| project-query exception | 不存在 ID 返回 NOT_FOUND | 响应状态及结构化错误；不能用 login-error |
| project-query boundary | 定位第二个 run-owned 项目 | 目标 ID/名称与种子对应 |
| page-navigation exception | 不存在入口未导航到目标 | 动作失败及原页面证据；不能仅凭一次重试 |
| page-navigation boundary | 目标创建表单可访问 | URL/表单元素/允许长度属性 |
| project-edit exception | 空名称被拒且原数据保留 | form-error + empty-name 错误 + 原记录不变 |
| project-edit boundary | 200 字符名称保存成功 | edit-success + 精确名称/ID + owned resource 结果 |
| form-validation exception | 空名称被拒 | form-error + empty-name 错误 + 数据不增加 |
| form-validation boundary | 200 字符名称创建成功 | success-message + 精确名称及长度 |
| form-validation recovery | 先重复名称失败，再修改成功 | 有序错误观察 → 最终成功 → owned resource 结果 |

上表是待批准业务 Oracle 设计，不是已签字的新 Ground Truth。实现时还须按范围选择浏览器结构化观察与可用的测试数据接口，不允许改正式 Oracle 来适配修复。

## 验收补强要求

批准并实现新版本后，24 组合必须逐项断言 test_case_verdict=PASSED、required expect 全通过、Trace 来源完整、清理结果明确；故意错误页面反例与观察丢失 INCONCLUSIVE 必须成立。保留旧 2.0.0 的历史复现实验，不能删除旧证据。未批准期间 C 只能记为部分完成，F 的六类场景业务验收不能宣称全部 PASS。


## 已获任务内批准后的实现

六个新增 Scenario 2.1.0 均要求显式 scenario_version，注册为 explicit_only；省略版本仍使用原默认版本。历史源码模块与当前模块的六个旧版 canonical digest 逐一完全一致。没有改写历史 Trace / 正式 TestCase。

PathSpec 增加可选 goal_definition / intent_templates，仅 >=2.1.0 可用；必须声明 required 断言、target 和有效字符串列表。API 执行、结构化目标复算、详情核验均使用路径目标；请求中显式非空要求优先，旧版请求行为不变。policies 仅增 scenario_versions 字段，Explorer 工作台可显式选择版本与四类路径，并由用户点击使用路径内置目标。

multi_step_goal 保持原 evaluator kind，补上真实观察顺序约束，拒绝倒序或重复快照；新增 first_after_previous 模式，从历史观察按顺序匹配声明的子断言，缺失为 INCONCLUSIVE，结果携带稳定 Evidence References。Recovery 要有异常观察在先、最终成功在后；page-navigation 另由测试中的实际失败动作与最终导航观察共同复核。

新版真实浏览器专项：6 组测试各运行四路径，24/24 PASSED。200 字符边界从真实 fill 值与最终页面全文核对；查询 boundary 的实际目标 ID 与 URL 核对；全部来源 hash、Scenario digest、PathSpec 与 goal_assertions 重读校验通过；owned data 清理后数据库无 TG_RUN_ 遗留。storage audit 再逐条计算实际 TestCaseVerdict，为 24/24 PASSED。全量门禁最终结果见总验收报告。

实现未将浏览器 UI 证据冒充独立后端业务 Oracle。原提案所列 backend 数据不变/计数的逐步运行中审计尚未全部产品化，当前由浏览器结果、动作值、源关联和清理后的真实数据库联合验证。旧版 11 次失败仍作为历史发现保留，不能声称旧版全部路径已修正。
