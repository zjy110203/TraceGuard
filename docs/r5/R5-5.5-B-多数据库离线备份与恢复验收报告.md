# R5-5.5 B：多数据库离线备份与恢复验收

状态：**实现与本机恢复语义验收通过**。工具只支持离线文件级备份，不声称在线一致性快照，也不自动切换生产配置。

## 备份格式与边界

- v2 manifest 明确记录 `topology=shared|separate`、角色、来源角色、备份 ID、UTC 时间、SQLite 文件数和每个 payload 文件的 SHA-256。
- shared 拓扑包含一个 Platform/SUT 共用 SQLite 数据库；separate 拓扑分别包含 Platform 与 TeamFlow SQLite 数据库。旧 v1 manifest 继续按 shared 拓扑读取。
- 创建前后重新扫描源文件并比较摘要；拒绝缺失角色、已有目标、源与目标递归、链接 / reparse point、SQLite WAL/journal 和无法通过 integrity check 的数据库。JSON / JSONL 也会逐文件解析。
- 恢复必须写入全新目录。恢复校验验证字节、SQLite、数据库拓扑、Alembic、TeamFlow / Platform 启动、表归属、历史数据引用、Evidence Blob 摘要、历史 API 读取，再启动 Chromium 跑一次真实业务流程并检查 cleanup。恢复检查全程不激活副本。
- Repair Sandbox 现为每次重放显式设置独立临时 `DATABASE_URL` 与 `TEAMFLOW_DATABASE_URL`，避免 sandbox replay 污染原始或恢复数据库。

## 离线操作

1. 停止 Platform、TeamFlow、后台 worker 与所有会写入部署目录的脚本。`--offline` 是操作员对停机条件的声明，不是工具对全部写入者的自动证明。
2. 创建 JSON 计划，明确 `topology` 并填写所有角色的绝对路径：shared 使用 `database`；separate 使用 `platform_database` 与 `teamflow_database`；两种都包括 `cases`、`candidates`、`explorations`、`chains`、`blobs`、`benchmark`。
3. 执行 `python -m scripts.local_backup create --source plan.json --destination <new-backup-dir> --offline`，然后执行 `python -m scripts.local_backup verify --source <new-backup-dir>`。
4. 在另一个全新目录执行 `python -m scripts.local_backup restore --source <backup-dir> --destination <new-restore-dir> --offline`。
5. 以 `python scripts/restore_check.py --backup <backup-dir> --work <new-check-dir>` 启动隔离语义检查。只有报告中每个必须检查均 PASS，才认为副本经过本地恢复验证。正式切换仍须按部署自己的变更程序独立进行。

工具不备份 `.env`、外置配置、密钥和不属于指定角色的目录，也不加密备份，不证明多机一致性或灾难恢复目标时间。失败恢复副本保留供调查；源数据从不覆盖。
