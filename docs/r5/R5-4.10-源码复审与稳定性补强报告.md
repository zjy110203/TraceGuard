## 1. 本轮源码审查结论

**总评：R5-4.9 的三项主修方向是对的，但"工程口径"整体被高估了一层。**

具体地说，R5-4.9 报告声称已解决的四件事（门禁口径、测试隔离、SSE 超时、清理健壮性），在源码层面都只完成了一半：

| 声称 | 源码事实 |
|---|---|
| 门禁 status 已改为 PASS/SKIP/FAIL/EMPTY | 四态缺 BLOCKED/NOT_RUN；EMPTY 仍被判为 `ok`，**不进退出码**；控制台与 report 状态**不同源**，会分叉 |
| 测试已隔离（不写正式库） | 用的是 `setdefault`：外部 `DATABASE_URL` 指向正式库时**原样继承**，仍会写正式库 |
| SSE 流不再中断 | 流本身修好了，但 `_SSEReader` 用 `timeout=None` 且只在收到数据后才检查 deadline —— 服务端静默时测试**挂死而非失败**，比失败更糟 |
| 清理健壮化 | `__exit__` 里 `self._pw.__exit__()` 无 try/except，抛异常会**直接丢掉整个 RunReport**；清理结果无任何结构化状态 |

结论分三级：

- **必须修（阻断交付）**：门禁状态语义、测试库隔离、`_SSEReader` 超时、`__exit__` 丢弃报告。
- **应当修（质量缺口）**：事件缺口不可检测、端口 TOCTOU、清理状态不可观测、并发无覆盖。
- **必须更正（口径失真）**：R5-4.9 把门禁 `FAIL` 写成 `BLOCKED`；README 存在**不存在的模块路径**与**不存在的产品能力**。

## 3. 根因与修复方案

### 3.1 统一验证入口（`scripts/verify_all.py`）

**根因**：状态不是"算出来的"，而是"各处各算一遍"。`ok` / `status` / 控制台打印三套逻辑并行，退出码又只看 `ok` 的一部分分支。

**修复**：
- `Step.kind` 区分 `command`（命令类）与 `test`（跑测试）。**命令类退出码 0 即 PASS，永不为 EMPTY**——它本来就不收集测试，"零计数"不是空。
- `StepResult.status` 成为唯一事实来源，六态：`NOT_RUN → EMPTY → PASS/SKIP/EMPTY → BLOCKED → FAIL`。
- `ok` 定义为 `status == "PASS"`；`compute_exit_code` 只看 `ok` —— **SKIP/EMPTY/BLOCKED/NOT_RUN 全部让退出码非 0**。
- 控制台、`report.json`、`report.md` 全部走同一个 `summary_line(result)` 与同一个 `status`。
- **BLOCKED 必须有证据**：只接受窄签名（缺模块、缺浏览器、`not installed under apps/web/node_modules`、端口占用）**且** exit≠0，命中文本写入 `blocked_evidence`。普通断言失败一律 FAIL——**不把失败降级成环境阻塞**，这是本轮最硬的红线。
- `_npm()/_node_bin()` 改为惰性调用，缺工具链记 `BLOCKED`（证据为异常文本）而不是 traceback；`TimeoutExpired` 同样转 BLOCKED（exit 124）。
- 失败中止时，剩余排队步骤逐个记 `NOT_RUN`（`ran=False`），报告与退出码都完整。
- 浏览器门禁启动 uvicorn 改为**端口冲突证据 + 3 次换端口重试**；只有健康检查通过才算启动成功，`passed` 未知时保持 `None`，不伪造数字。

**验证**：`tests/test_verify_gate_status.py`（11 项）覆盖状态组合，包括"普通失败必须不是 BLOCKED""PASS+EMPTY 的退出码非 0""三处状态字符串完全一致"。

### 3.2 数据库测试隔离（`tests/conftest.py`）

**根因**：`setdefault` 的语义是"外部值优先"，它保证了 verify_all 注入的隔离库生效，但**无法区分**外部值到底是隔离库还是正式库。安全性被交给了运气。

**修复**：
- `is_safe_test_db_url(url, repo_root=...)` 纯函数：只接受 `sqlite:///`；拒绝 `data/` 及其子目录；要求父目录可写；返回 `(ok, reason)`。
- 继承值必须**同时**满足"安全"与"被标记为测试库"（`.traceguard-tmp/` 下、系统临时目录、或 `TRACEGUARD_TEST_DB=1`）才沿用，否则**强制覆盖**；`DATABASE_URL` 与 `TRACEGUARD_DATABASE_URL` 强制同值。
- 清理失败写 `.traceguard-tmp/pytest-cleanup-failures/<时间>-<pid>.json` 并 `warnings.warn`，**不静默**。
- 顺带修掉 N7 的真实成因：会话末尾先 `dispose()` 模块级 app（`apps.api.main` / `apps.teamflow.main`）的 engine，再做有界重试删除。修前每次运行必留一条 `WinError 32`；修后正常路径不再产生记录（新增的 3 条记录全部来自测试自身的注入用例）。

**验证**：`tests/test_db_isolation.py`（12 项）——子进程污染测试（env 双指向正式库）、正式库 `SHA-256 + size + mtime_ns` 前后全等、清理成功/失败双分支、6 个安全校验用例。

### 3.3 SSE 测试质量与生命周期

**4.1 测试独立性**：`test_last_event_id_replays_only_later_events` 原本断言 `len(history) >= 3`，依赖前面测试的产物。改为自建 5 条合成事件、**自证序号连续与 id 唯一**、取中间一条作游标，断言回放集合**精确等于**其后的事件。单用例独立运行通过（2.61 s）。

**4.2 读取超时**（N8 根因）：`httpx.Client(timeout=None)` 让 connect/read 都无限等待，deadline 只在 `iter_lines()` 返回一行后才被检查——零数据时永远检查不到。

修复为四层：
1. `connect` 超时、2. 单次 `read` 超时、3. **总时长看门狗**（`threading.Timer(max_seconds, abort)`，与是否收到数据无关）、4. `stop()` 主动关闭（对真实 socket 做 `shutdown`，避免 Windows 上半死连接让服务端以为客户端还在）。
外加：线程必退、`done` 必 set、`timed_out` 与 `error` 分离、新增 `started_at/last_line_at/finished_at` 便于诊断。

**4.3 事件丢失检测**（N9 根因）：丢事件发生在 `except queue.Full: pass`，且"尾部丢失"在下一条事件到来前根本无从发现。

修复（**未改 C05 事件字段**）：
- `SubscriberQueue` 记账：`dropped`、`dropped_ranges`（区间合并、上限 100）；
- `EventBus.dropped_total`、`subscriber_stats()`、`dropped_ranges()`；
- 缺口以 **SSE 注释帧** `: gap from=.. to=.. dropped=..` 上送 —— SSE 规范要求客户端忽略 `:` 开头行，因此**对现有 C05 消费者完全兼容**；
- 空闲轮询时若**已记录**丢弃也立即上报（否则突发丢弃后再无新事件时缺口永不可见），但只上报与"下一个期望序号连续"的区间，避免把仍在队列里的事件误报为丢失；
- 纯函数 `audit_event_sequences()`（`packages/execution/eventaudit.py`）覆盖：缺口、重复、乱序、连续、空输入；`monotonic`（严格递增）与 `contiguous`（无缺口）分开，才能区分"乱序"与"中间缺失"。

**4.4 持久化历史（只调研 + 设计，未实施）**

现状（已核实）：
- `EventBus._history` 是**纯进程内 list**，与 `_sequence` 同生命周期；`/api/v1/events` 与 `Last-Event-ID` 回放都只读它。
- **`Last-Event-ID` 解析不到时回落 `after_seq = 0`，即全量重放**（不是空）。本轮补了 `logger.warning("sse_unknown_cursor")` 让它可观测，**行为未改**。
- 重启后 `sequence` 从 1 重新开始、`event_id` 全新。客户端若按 `sequence` 比较去重，会把自己的 57 当成比 1 更新而**静默丢事件**；若按 `event_id` 去重，则把全量当新事件重复处理。

可复用的持久化设施：`packages/evidence/events.py` 的 `EventStore`（`EventRow` 表 + Outbox + ConsumerInbox + `detect_sequence_gaps`），与 workbench 共用同一个 `app.state.engine`，**已持久化**，`chain_api` 已在用。但它存的是 `EventEnvelope`（含 `producer_instance_id`/`idempotency_key`/`workspace_id`），与 `RunEvent` 形状不同，**不能直接复用表结构，可复用机制**。

兼容性设计要点（供评审，本轮不实施）：
1. `EventBus` 增加可选 `store`（默认 `None`），`publish` 先 append 再 fan-out；`RunEvent` 字段不动，映射 `producer_instance_id=worker_id`、`idempotency_key=event_id`、`workspace_id` 取自服务端受信上下文（**绝不从 payload 取**）。
2. 游标升级为双段：`Last-Event-ID` 仍接受 `event_id`，解析出 `(producer_instance_id, sequence)`；未知时不再静默回落 0，而是"从保留窗口最早处回放 + `: cursor-unknown` 注释帧"。
3. 顺序：`EventStore.sequence` 是 **per producer_instance** 唯一，而 `RunEvent.sequence` 是进程全局；映射到 `worker_id` 后语义正好对齐"重启换实例、序号空间不复用"。注意 `EventStore.query` 按 `observed_at` 排序，跨实例回放须改按 `(producer_instance_id, sequence)`。
4. 需要显式保留窗口，才能区分"游标过期"与"确实没有事件"。

### 3.4 浏览器资源清理状态（N10/N11）

**根因**：清理结果只有瞬时事件，没有任何结构化状态；`__exit__` 的 Playwright 停止环节还能抛异常把报告整个丢掉。

**修复**：
- 新增 `CleanupStatus`：`browser_closed` / `browser_close_error` / `trace_stopped` / `trace_stop_error` / `evidence_errors` / `page_crashed` / `page_crash_detail` / `execution_cancelled` / `cancellation_reason` / `playwright_stopped` / `playwright_stop_error` + `problems()` + `is_clean` + `to_dict()`。
- `__exit__` 重写为三段独立 try/except（trace 停止 / 浏览器关闭 / Playwright 停止），**任一步失败都不阻断下一步**，函数体**永不含 raise**，`finally` 里把四个句柄全部置空。
  精确边界：捕获的是 `Exception`；`SystemExit` 一类 `BaseException` 仍会穿透。这一点与 sandbox 的清理刻意不同——那里 `rmtree` 会被宿主删除守卫以 `SystemExit` 中断，所以单独捕获；浏览器清理不删目录，触发不到该路径。
- 每个失败都做三件事：写状态、emit 事件（保留 `evidence.trace.failed`、`browser.close.failed` 原名，新增 `browser.playwright.failed`）、`logger.error`。**不静默**。
- `RunReport.cleanup` 承载快照；不干净时 emit `run.cleanup.degraded` 并把说明追加进 `verdict_notes`。
- **两个维度严格分离**：清理失败**不改**业务 verdict；`is_clean` 只回答"资源是否全部释放"，因此**取证失败不计入 `is_clean`**（浏览器健康、无资源悬空），但仍在 `evidence_errors` 与 `problems()` 里，信息不丢。页面崩溃与执行取消同样各自独立表达。

**验证**：`tests/test_browser_resilience.py` 4→9 项，覆盖任务要求的 6 类异常注入（正常关闭 / 关闭失败 / 页面崩溃 / Trace 失败 / 截图失败但业务成功 / **清理中再抛异常**），外加执行取消。

### 3.5 动态端口统一（N12/N13）

**根因**：`free_port()` = bind → 读端口 → **close**，调用方再 bind。关门到开门之间端口无主。模块级 `TF_PORT` 在导入期就 close，而 OS 优先复用刚释放的端口，于是两个模块极易拿到同一个号。

**修复**：
- `tests/netutil.py` 新增 `reserve_port()`（socket **全程持有**）、`take_reserved()`（交给 `uvicorn.Server.run(sockets=[...])`）、`release_reserved()`；`serve_uvicorn()` 上下文管理器一步到位，`stop_uvicorn()` 断言线程已死。
- 15 个测试模块 + `tests/e2e/test_user_journey.py` 全部改为预绑定 socket；`TF_PORT` 常量名保持不变，调用方零改动。
- `test_network_gateway` 两个 origin 改为各 `reserve_port()` 并存，**保证二者不同**。
- 子进程（`packages/execution/sandbox.py`、`scripts/e2e_product_flow.py`）无法共享 socket，改为"端口冲突证据（`address already in use` / `errno 98` / `errno 10048` / `winerror 10048`）+ 3 次换端口重试"，并**区分**"冲突"与"进程活着但不健康"（后者不重试，那是真 bug）。

### 3.6 并发可靠性（新增）

## 8. 已知限制

1. **SSE 历史仍是进程内 `list`**，重启即丢；`Last-Event-ID` 未知时静默回落 0（全量重放）。设计已给出（§3.3-4.4），**未实施**。
2. **`dropped=` 语义**：定义为"这段缺口里、本订阅队列确实记过的丢弃数"（0 表示缺口来自别处，如重启/历史丢失），不是缺口大小。若前端要显示"你丢了 N 条"，需再加 `missing=`。
3. **尾部丢失主动上报**：空闲轮询时也会发 gap 注释帧（否则突发丢弃后再无事件则永不可见）。若要求"无 data 帧就不该有注释帧"，可退回严格版，代价是该用例要改成"丢完再发一条"。
4. **C04 `cleanup` 属契约变更**，`additionalProperties: false` 的旧严格校验器会拒绝新 payload，待评审（§5.2）。
5. **`RepairSandbox` 历史目录**：`.traceguard-tmp/r3` 下已有 180 个历史目录，按"不删历史数据"原则保留；新逻辑不再累积。
6. **并发测试是"有限并发"**，不是压测：最多 4 客户端 / 4 Run / 8 写线程，单进程。Redis/Celery 仍为 `BLOCKED`（D8 范畴），Dispatcher 仍是单机线程池。
7. **真实 LLM 未接入**：Explorer `llm` 策略仍 409，benchmark LLM 基线为 `NOT_RUN` 占位。
8. **GT 未批准**：6 条记录全部 `UNRESOLVED`，准确率指标保持 `None(BLOCKED)`。
9. **本机删除守卫**会让"一次调用里删太多"失败，长验证序列必须拆成独立调用——这是环境事实，已写进 `resume.md`。
10. **未做**：真实 DeepSeek 调用、外部网站测试、Redis/Celery、正式库清理、自动 commit/push/merge。
