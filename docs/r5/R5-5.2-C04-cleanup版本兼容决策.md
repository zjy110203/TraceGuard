# R5-5.2 C04 `cleanup` 版本兼容决策（D-R5-411-3 收口）

> 状态：决策已定，测试已固化；继承 R5-4.11 决策 D-R5-411-3，本轮补齐"旧/新消费者如何各自消费"的操作口径。
> 范围：只处理 C04 `RunReport.cleanup` 的增量兼容。**不修改 C05，不扩大任何其他契约字段**。
> 基线：`r5-5-product-completion` @ `37ecfbf`。

## 1. 问题与禁止项

C04 在 R5-4.10 增加了 `RunReport.cleanup`（资源清理状态，含 `browser_closed` / `trace_stopped` /
`playwright_stopped` / `evidence_errors` 等），目的是让"浏览器关闭失败"这类资源问题**不污染业务 verdict**。

风险点：C04 顶层 `additionalProperties: false`。新增 `cleanup` 后，**持有旧 schema 缓存的严格校验器**
会拒绝新 payload——这是真实的兼容断裂，不能假装它不存在。

本决策明确**不做**三件事：

1. 不删除 `cleanup`（删除会让资源清理失败重新变成不可观测，回退 R5-4.10 的修复）；
2. 不把"旧消费者拒绝新字段"粉饰为兼容（它是已知残留风险，见 §5）；
3. 不把 cleanup 状态塞进 `test_verdict` 或 C05 事件（两者语义必须分离，已有测试钉住）。

## 2. 事实核对（决策依据）

| 核对项 | 实际情况 | 来源 |
|---|---|---|
| C04 Schema | `cleanup` 在 `$defs.RunReport.properties` 中，`additionalProperties: true`（内部可扩展）；**不在 required** | `packages/contracts/schemas/C04_Execution.schema.json` |
| 顶层约束 | `RunReport.additionalProperties: false`，required 仅 `run_id/case_id/case_version/started_at` | 同上 |
| 注册表版本 | C04 `0.2.0-draft` / `status=draft`（C05 同为 `0.2.0-draft`，未被改动） | `packages/contracts/registry.json` |
| 新生产者 | `run.runner` 在 `report.cleanup = browser.cleanup.to_dict()` 写入；`pipeline.apply_cleanup` 再合并 plan/applied/status_code | `packages/execution/runner.py`、`pipeline.py` |
| 旧生产者 | 不写 `cleanup` 键（字段有 `default_factory=dict`，但旧序列化路径产出无该键的 payload） | 兼容测试 `test_legacy_payload_without_cleanup_still_validates` |
| 旧消费者 | 按旧字段读取 `run_id/case_id/steps/test_verdict` 等；不认识 `cleanup`，遇到即校验失败（仅当它做严格 schema 校验时） | `test_stale_validator_rejects_the_new_payload` |
| 新消费者 | 前端 `RunReport.cleanup?: CleanupStatus` 可选；`RunDetailView` 分区展示资源状态 | `apps/web/src/api/types.ts` |
| 不可混轴 | `cleanup` 内不得出现 `test_verdict/verdict/passed/failed`；C05 不含 `cleanup` | `tests/test_contract_compat_c04.py` |

## 3. 版本兼容决策（核心）

**决策编号 D-R5-411-3（收口）**：`cleanup` 保持为 **严格增量的可选字段**，契约版本沿用 `0.2.0-draft`，
不新增 version 字段、不引入内容协商头。理由：C04 仍为 draft，字段可选且旧 payload 仍合法，
升级成本集中在"缓存旧 schema 的严格校验器"这一类，用部署纪律解决比扩契约更划算。

### 3.1 生产者侧（新/旧）

- **新生产者**：继续写 `cleanup`；只当**可忽略的附加信息**——任何消费者丢弃它都不影响业务 verdict。
  不得在其中携带 verdict 语义（已有测试断言）。
- **旧生产者**：不写 `cleanup` 的 payload 继续有效，新 schema 不要求该键（兼容测试已钉住）。
  不需要回填历史数据。

### 3.2 消费者侧（操作口径，这是本轮补齐的部分）

| 消费者类型 | 处理方式 | 是否改代码 |
|---|---|---|
| 宽松消费者（只看已知字段、忽略未知字段，如当前前端） | 直接消费：`cleanup` 缺失时按"未提供清理状态"处理，不报错；存在时分区展示资源状态 | 否 |
| 新严格消费者（加载当前 registry 的 schema） | 正常校验通过；读取 `cleanup` 时用可选访问，不得把它当 verdict 输入 | 否 |
| **旧严格消费者（缓存了 pre-R5-4.10 schema）** | **必须刷新 schema 缓存后重验**；在刷新前，它拒绝新 payload 是**预期行为**，不得通过降低断言、裁剪字段或改判 FAIL 来绕过 | 部署动作：清缓存 / 重启以加载新 registry |

### 3.3 是否引入版本协商

**不引入。** 最小方案已足够：

1. 旧 payload（无 cleanup）合法 → 老数据无需迁移；
2. 新 payload（有 cleanup）在**当前 schema** 下合法 → 新消费者无需分支；
3. 唯一失败面是 schema 缓存陈旧 → 由部署时刷新缓存解决，并写入运行手册。

若未来 C04 冻结（status 从 draft → frozen）或出现第二个不兼容字段，重新评估版本协商；
届时只在 C04 内引入 `schema_version`，**不动 C05**。

## 4. 测试固化（兼容包络）

`tests/test_contract_compat_c04.py` 把上述决策逐条钉住，共 8 项：

- `test_current_payload_with_cleanup_validates` — 新 payload 合法；
- `test_legacy_payload_without_cleanup_still_validates` — 旧 payload 仍合法；
- `test_cleanup_is_optional_and_never_required` — cleanup 非 required、C04 仍 draft；
- `test_unknown_top_level_field_is_still_rejected` — 顶层严格性未被削弱；
- `test_stale_validator_rejects_the_new_payload` — **已知残留风险被固定为事实**，不是被修复的缺陷；
- `test_c05_event_contract_is_untouched` — C05 零改动；
- `test_cleanup_does_not_carry_business_verdict` — cleanup 不含 verdict 语义。

## 5. 已知残留风险与登记

- **残留风险**：缓存旧 schema 的严格校验器拒绝带 `cleanup` 的 payload。缓释 = 部署时刷新 schema 缓存 / 重启；
  该行为由 `test_stale_validator_rejects_the_new_payload` 显式证明并保留，禁止用"放宽断言"消除。
- **不是本轮缺陷**：C04 仍为 draft，尚未冻结；冻结时需重新评审本决策。
- **不扩散**：本决策不触及 C05 事件形状、不新增 SSE 字段、不扩大探索/Candidate 契约范围。

## 6. 与其他整改项的关系

- 与 P1-2（SSE 游标协议）：`stream.notice` 是传输层控制事件，不是 `RunEvent`，因此同时不触及 C04/C05；
  C04 的 cleanup 是 Run 报告层，两层正交。
- 与 P0-2（序号分离）：`sequence: None` / `durable:false` 只出现在事件 `data:`，不进入 RunReport.cleanup。
