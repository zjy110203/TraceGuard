# R5-5.5 源码复审与可靠性收口

范围：独立业务状态证据、TeamFlow/Sandbox 数据隔离、多数据库离线备份恢复、显式 opt-in 场景路径，以及 Repair / Benchmark 准入边界。R6 预存工作树改动不属于本次交付，也不纳入提交。

## 复审发现与处置

1. **分库部署下 Sandbox 可能继承 Platform `DATABASE_URL`。** TeamFlow child process 除兼容变量外未覆盖两项 Settings 实际读取的 URL；真实回放会在 Platform DB 创建 SUT 表。Sandbox 现在将 `DATABASE_URL`、`TEAMFLOW_DATABASE_URL` 和 `TRACEGUARD_DATABASE_URL` 都重定向到每个 sandbox 的临时 SQLite 文件。手工闭环与 restored separate topology 均通过 schema 归属检查。
2. **全局 ORM Base 导致跨服务 `create_all` 风险。** TeamFlow startup 现在仅创建显式列出的 SUT / Eval 表；独立恢复检查分别核对 Platform 12 表与 TeamFlow 7 表，并拒绝另一侧的表出现在错误数据库。
3. **新建未迁移的 Platform schema 恢复处理。** Restore checker 只在确认当前证据表具备最新 attachment 字段时标记 Alembic head；部分旧 schema 继续从 base 执行迁移，冲突或不完整 schema fail closed。
4. **历史资料不可只看文件摘要。** Restore checker 还核对 Exploration trace hash、Candidate transaction 正式文件 / 版本关系、Chain/Run/Case/Evidence 关系、Blob 内容地址摘要和 Repair journal 中的事务资产，再通过恢复后的 API 重读历史。
5. **独立业务状态证据故障不得变成产品测试失败结论。** 状态读取失败保留 `UNAVAILABLE` / `INCONCLUSIVE`；不可确认的业务状态不会改写执行 Verdict、Oracle 或 Trace。cleanup 错误保留 ownership 供后续恢复。
6. **静态类型检查暴露 ORM Table 类型不匹配。** TeamFlow `create_all(tables=...)` 的模型表显式窄化为 SQLAlchemy `Table[Any]`，全量 MyPy 可继续执行。
7. **Windows 后续删除 SQLite 备份文件失败。** SQLite connection 的 context manager 只负责事务提交 / 回滚，不会关闭连接；备份校验现对只读连接显式调用 close，避免后续文件复制或删除被占用。

- 聚焦 backup / restore 与人工 Repair 综合场景通过 17 passed；SQLite 句柄关闭修复包含在最终快照。
- 最终 `verify_all.py --mode all --build-web` 在隔离 R5-only worktree **PASS**：Ruff / format / MyPy、pytest 973 passed / 4 skipped、前端依赖 / 类型 / build、安全 216 passed、Product 24 passed、Browser 150 passed。
- 深层 Windows 临时路径导致首次 isolated run 在备份复制与 lease 写入中遇到路径上限；短 basetemp 的最终 aggregate 通过。该运行参数与输出目录已记入 [验证报告](evidence/r5-5.5/verify-all-20261127.md)。早期格式 / 类型失败和含预存 R6 UI 的原工作树失败均是被 supersede 的独立尝试，不作为通过结果。

## 剩余限制

系统仍是单机单进程产品边界；离线数据库备份要求操作者停止所有写入者；本轮不提供在线一致性快照、密钥管理、跨主机数据库复制或灾备演练。Generator 仅形成准入设计，GT 与准确率仍 `BLOCKED`，D8 仍禁止真实 LLM 接入。
