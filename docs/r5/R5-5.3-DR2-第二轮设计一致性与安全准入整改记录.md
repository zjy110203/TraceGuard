## 2. DR2-01～DR2-12 逐项整改记录

### DR2-01：分离 GoalStatus 与 TestCaseVerdict（P0，最重要业务语义）

**问题**：原设计将业务目标达成与测试用例通过混为一谈。异常路径预期 goal `NOT_VERIFIED`，
但系统正确拒绝非法操作时测试本身应 PASSED——原设计无法表达这一点。

**修订前**：
- goal `NOT_VERIFIED` 被隐式当作测试失败；
- 无独立的测试用例判定字段；
- 异常路径无法形成有效测试证据。

**修订后**：新增 §3.6（GoalStatus 与 TestCaseVerdict 分离）。

| 判断 | 域 | 取值 | 裁决者 |
|---|---|---|---|
| GoalStatus | 被测业务目标 | VERIFIED / NOT_VERIFIED / INCONCLUSIVE | Goal Evaluator（断言求值） |
| **TestCaseVerdict**（🆕） | 本条测试用例 | PASSED / FAILED / INCONCLUSIVE | **独立证据断言**（非 Agent 裁决） |

**求值规则**：
```
goal_status == INCONCLUSIVE → test_case_verdict = INCONCLUSIVE
goal_status == expected_goal_status 且 expect 全 PASSED → test_case_verdict = PASSED
否则 → test_case_verdict = FAILED
```

**四类路径合法样例**（见 §3.6.3）：
- 正常：expected=VERIFIED，goal=VERIFIED → PASSED
- 异常：expected=NOT_VERIFIED，goal=NOT_VERIFIED + 错误反馈可见 → **PASSED**（负向测试通过）
- 边界：按声明（200 字符成功 / 201 字符校验错误）
- 恢复：expected=VERIFIED，故障反馈曾出现 + 恢复成功 → PASSED

**负向测试证据链**：路径声明 expected + GoalStatus 求值记录 + expect 证据断言逐项 PASSED
+ TestCaseVerdict 求值记录 + 证据路径完整 → 构成"系统行为符合预期"的有效测试证据。

**与 Candidate Compiler 关系**：编译准入从"goal VERIFIED"扩展为"TestCaseVerdict=PASSED"。
正常路径 PASSED ⟺ goal VERIFIED（旧语义完整保留）；异常路径允许 goal NOT_VERIFIED + PASSED 准入。
**标记为需项目负责人确认的决策**（见 §10）。

**非法样例**：Agent 自行声明 TestCaseVerdict → 拒绝；NOT_VERIFIED 自动映射 FAILED → 禁止；
路径缺 expected_goal_status → 拒绝注册。

**受影响接口**：GoalEvaluator 输出（台账 §6.2）、Compiler 准入条件、M2 验收门槛。

### DR2-02：封堵 PolicyValidator 到 ToolGateway 的绕过路径（P0）

**问题**：PolicyValidator 负责场景约束，ToolGateway 不负责场景约束。
内部调用者绕过 PolicyValidator 直接调用 ToolGateway 可跳过 `allowed_actions`/`denied_actions` 检查。

**修订前**：ToolGateway 只做 URL/selector/value/预算校验，不验证"谁批准了这个动作"。

**修订后**：引入**执行授权凭证（Execution Authorization Token）**（§4.3）。

凭证绑定：run_id、decision_id、scenario_id、scenario_version、action、args_digest（规范化参数摘要）、
budget_state_version、expires_at、nonce（一次性）。

**ToolGateway 执行前必须验证 6 项**：
① 凭证来自受信 PolicyValidator（HMAC 签名）；② 属于当前 Run；③ Action 与 args_digest 一致；
④ Scenario Version 一致；⑤ 未过期、未重复消费（nonce）；⑥ 预算状态版本未变。

验证失败 → 拒绝（`invalid-authorization`）。ToolGateway 仍负责 URL/OriginPolicy/selector/value/预算
权威安全校验——凭证是增加一层，不替代、不放宽。

**危险操作策略修订**：
- 通用 click 不能仅凭工具名称判断业务影响（场景标注 selector 业务影响级别）；
- 删除/清空/破坏性提交不能靠重复次数判断安全；
- **首期默认禁止未明确授权的破坏性操作**（`destructive_authorized` 默认 false）；
- 放行需三项全满足：场景显式授权 + 测试数据隔离 + 执行范围满足。

**5 类非法样例（全部拒绝）**：

| # | 非法行为 | 检测点 | reason_code |
|---|---|---|---|
| 1 | 直接绕过 PolicyValidator 调用 ToolGateway | 无授权凭证 | `invalid-authorization` |
| 2 | 伪造 PolicyDecision | HMAC 签名验证失败 | `forged-decision` → POLICY_STOP |
| 3 | 修改参数后复用授权 | args_digest 不一致 | `args-mismatch` |
| 4 | 跨 Run 使用授权凭证 | run_id 不匹配 | `cross-run-token` → POLICY_STOP |
| 5 | 重复消费授权凭证 | nonce 已消费 | `token-replayed` → POLICY_STOP |

**不削弱现有 ToolGateway 和 OriginPolicy**（明确确认）。

### DR2-03：明确 Secret Reference 机制（P0）

**问题**：`fill` 要求 `value` 必填，但 D8 规定密码不能进入模型上下文——两者矛盾。
现有 `value_ref` 是脱敏产物（`sanitize_action` 保留的标记），无授权语义，不能承担秘密引用职责。

**修订后**：设计独立的 `secret_ref`（§4.2）。

| 项 | 规则 |
|---|---|
| 非敏感输入 | 允许模型提供 `value` 明文 |
| 敏感输入（密码/Token/凭据） | **禁止**明文 `value`；只能提交 `secret_ref` |
| 命名空间 | `secret://{scenario_id}/{secret_name}` |
| 允许集合 | 场景声明 `secret_refs` 列表；引用必须在集合内 |
| 引用权限 | 不允许通过任意环境变量名称读取服务器秘密（`env://` 拒绝） |
| 解析 | 服务端受信 Secret Resolver，执行阶段解析 |
| 注入时机 | 真实值仅执行阶段注入 ToolGateway，不回传模型 |
| 模型上下文 | Proposal/DecisionContext/prompt 只含 `secret_ref` 字符串 |
| Trace/日志/错误 | `secret_ref` 进 Trace（引用记录）；真实值永不进入 |
| 解析失败 | `SECRET_RESOLUTION_FAILED`，拒绝执行 |
| 无权限引用 | `SECRET_ACCESS_DENIED` + `unauthorized-secret-ref`，POLICY_STOP |
| 重放 | 重新解析；秘密已轮换 → 标注 `secret-rotated`，不伪造历史值 |

**`value_ref` vs `secret_ref` 区别**：value_ref 是脱敏标记（Compiler 绑定用）；
secret_ref 是授权引用（Secret Resolver 解析）——两者职责不同，不得混用。

**合法/非法样例**：见 §4.2（敏感 selector 用 value → 拒绝；value_ref 冒充 → 拒绝；
未声明引用 → 拒绝；env:// → 拒绝）。

### DR2-04：修正测试数据清理的并发安全问题（P0）

**问题**：原方案 B"按命名前缀扫描孤儿数据"——下次运行扫描 `种子项目-form-validation-*` 时
可能误删另一个**正在运行**的 Run 的种子数据。命名前缀不能作为孤儿判定依据。

**方案评估**：

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| A. 每 Run 独立测试数据库 | 天然隔离 | 需 SUT 支持多 DB 拓扑，改造超范围 | 不选 |
| **B′. 共享隔离测试库 + run_id + 活动租约 + 清理锁** ✅ | 不改 SUT DB 拓扑，可验证性高 | 需租约机制 | **选定** |

选 B′ 的理由：A 要求 TeamFlow 支持多 DB（超出 SUT 最小改造范围，现有 service 绑定单 DB session）；
B′ 在共享测试库上用租约机制解决并发安全，改造面最小。修订 B 是因为原"前缀扫描孤儿"有并发缺陷。

**B′ 机制（8 项）**：run_id 唯一、数据所有权（只有创建者可清理）、活动租约（心跳 ≤30s）、
孤儿判定（租约 released 或心跳超时**且**不在活动进程列表，**禁止仅凭前缀**）、
活动保护（active 租约数据不许他 Run 清理）、清理锁（同一时刻仅一个清理者）、
并发隔离、清理失败登记 CLEANUP_FAILED。

**5 个必答场景**（见 §2.4）：
1. 两个 Run 并发：各自独立 run_id+租约，互不触碰；
2. Run-A 正常结束、Run-B 运行中：Run-A 只清自己的，Run-B 受保护；
3. 进程崩溃恢复：租约心跳停止→超时→判孤儿→下次清理（持锁）；
4. 清理中再崩溃：删除幂等，残留数据下次继续，锁超时释放；
5. 重复运行/重复清理：新 run_id 不冲突，重复清理 no-op，CLEANUP_FAILED 重试有上限。

**禁止通过 `reset_data()` 清空正式数据**（不变）。

### DR2-05：明确 Scenario Path 与动态 Agent 的关系（P0）

**问题**：paths 仍用固定步骤列表，但真实 Agent 需要动态规划——两者混淆。

**修订后**：三概念分离（§2.5.2）。

| 概念 | 定义 | 载体 |
|---|---|---|
| **A. Path Specification** | 目标、前置条件、预期行为、允许操作、覆盖要求 | `paths.*` 条目的非步骤字段 |
| **B. Scripted Fixture** | 仅确定性测试/回归的固定 Action 步骤 | `scripted_fixture` 可选字段 |
| **C. Real Agent Planner** | 根据 Observation/历史/预算/约束动态生成 Proposal | `propose(context)` |

**红线**：Real Agent 不得退化为读固定 steps；固定脚本不得冒充自主探索；
每种路径必须描述预期行为（`expected_goal_status` + `expect`）；
覆盖要求不能变成强制动作脚本；Scripted/Mock/Real 三来源必须区分；
**M3 必须证明 Observation 改变后 MockProvider 的 Proposal 随之改变**（Mock 是观测响应式）。

**统一数据结构样例**：见台账 §9-A（`paths.normal/exception/boundary/recovery` 各条含
`path_id`/`goal`/`expected_goal_status`/`expect`/`coverage`/`scripted_fixture`）。

### DR2-06：补齐 Scenario Version 的历史身份保障（P0）

**问题**：原设计"无版本 Trace 视为 1.x 历史，按最低已实现版本解释"——不能证明历史 Trace
对应的实际场景定义，有伪造历史解释的风险。

**修订后**（§2.2/§2.2.1）：
1. 新 Scenario Package 规范化 JSON 序列化（`json.dumps(ensure_ascii=False, sort_keys=True)`）；
2. `scenario_digest` = SHA-256；
3. 新 Trace 保存 `scenario_id` + `scenario_version` + `scenario_digest`；
4. Hash v3 覆盖上述三字段；
5. 相同版本行为定义不得静默修改（digest 不一致 → 拒绝）；
6. 行为变化必须升版本；
7. 历史无版本 Trace → `legacy-unversioned` 显式标记（**不**绑定任何版本，不按最低/最新版本伪造解释）；
8. 无法确定历史定义时不得用当前最新版本伪造历史；
9. 三种错误语义区分：`LEGACY_UNVERSIONED`（标记）/ `SCENARIO_DIGEST_MISMATCH`（内容被改）/
   `UNSUPPORTED_SCENARIO_VERSION`（版本不存在）。

**SemVer 规则**：行为不兼容升 Major；向后兼容能力增加升 Minor；仅非行为修订升 Patch。

**签名评估**：首期不需要数字签名。信任边界 = 场景包随代码发布，来源由构建/发布流程保证。
`scenario_digest` 只提供**内容完整性校验**，**不提供发布者真实性认证**。
不得宣称仅凭 SHA-256 具备发布者身份认证。若未来引入用户上传/远程场景源，必须另行引入签名。

### DR2-07：统一 D8 Provider 与 Kill Switch 设计（P0）

**问题**：D8 文档内部矛盾——§0"一键关闭立即回退" vs §10"需重启" vs §11.2"立即/下一决策环"混用；
§2.2"任何 OpenAI 兼容端点" vs §2.3 白名单。

**修订后**：
1. **统一 Kill Switch 口径**：环境变量 + **重启服务**生效，无运行时热切换。
   §0/§10/§11.2 全部统一为"重启后生效"；删除"立即""下一决策环"等不一致描述。
2. **统一 Provider 口径**：首期只允许正式批准的精确 endpoint（`api.deepseek.com/v1`、`api.openai.com/v1`）；
   不允许"任何 OpenAI 兼容端点"；新增 Provider 或改变 endpoint 必须重新走 D8 审批。
3. **DNS rebinding 实际实现要求**：连接前解析 IP 校验非内网 + 连接时绑定已验证 IP + 禁止非批准重定向 +
   HTTPS 证书校验（不只写"复用 UrlGuard"）。
4. **重启期间行为明确**：进行中请求中断、Provider 侧调用可能完成但结果不采纳；
   已返回未执行的 Proposal 丢弃（记 `discarded-on-shutdown`）；已持久化 Trace 保留。
5. **权限明确**：启用/关闭 = 运维/负责人（环境变量+重启）；紧急情况任何发现异常人员可触发关闭。
6. **密钥轮换**：环境变量替换+重启；紧急停用流程四步。

**D8 仍是独立人工审批门禁，409 BLOCKED 不解除。**

### DR2-12：分离 Preconditions 与 Data Lifecycle（P1）

**问题**：原设计让数据生命周期适配器统一执行 preconditions，混淆"数据准备"与"前置检查"。
数据契约 `data_setup.provider: "teamflow-api"` 与 DB Fixture 方案矛盾。

**修订后**（§2.5.3）：三者分离——

| 职责 | 组件 | 失败状态 |
|---|---|---|
| Data Setup（数据准备） | 数据生命周期适配器 | `SETUP_FAILED` |
| Precondition Evaluator（前置检查） | 独立检查器 | `PRECONDITION_FAILED` |
| Cleanup Adapter（清理） | 数据生命周期适配器 | `CLEANUP_FAILED` |

执行顺序：Setup → Precondition → 探索 → Cleanup（finally 语义）。
`data_setup.provider` 修正为 `data-lifecycle-adapter`（不再是 `teamflow-api`）。
