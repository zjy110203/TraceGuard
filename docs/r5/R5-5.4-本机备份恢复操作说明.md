# R5-5.4 本机离线备份恢复

状态：最小实现；隔离临时数据自动化验证。不是在线一致性快照，不进行用户正式数据恢复演练。

现有 restore_check.py 仅验证单个数据库备份，无法涵盖 Candidate、正式 Case、Repair journal 和证据文件。本轮新增 scripts/local_backup.py，覆盖七个角色：database（SQLite 文件）、cases、candidates、explorations、chains、blobs、benchmark（含 diagnoses / repairs.jsonl / GT）。Event/Audit 数据在平台 SQLite；如 SUT 使用独立数据库，应停止 SUT 后另纳入受控备份方案，本工具不宣称覆盖独立 SUT DB。

1. 停止 API、SUT 与所有写入脚本。--offline 是操作者的停机前提声明，不是程序自动证明服务已停止。
2. 准备 plan.json，严格包含七个角色到实际部署路径的映射，使用绝对路径，目录可为空但必须存在。独立配置目录没有对应角色，plan 不接受第八个键。只有位于上述角色目录内部并进入 manifest 的普通配置文件随角色备份。部署根目录的 .env、外置配置和密钥文件均须按单独批准的配置管理流程核对，本工具不能证明配置已完整备份。
3. `python -m scripts.local_backup create --source plan.json --destination <新备份目录> --offline`。
4. `python -m scripts.local_backup verify --source <备份目录>`。
5. `python -m scripts.local_backup restore --source <备份目录> --destination <新恢复目录> --offline`。
6. 检查 manifest.json / restore-result.json，按 payload 下的角色路径配置一个隔离实例后另执行应用语义验收；工具不会切换正式配置或覆盖当前数据。

备份前后源目录清单和 SHA-256 必须一致，复制内容须与源摘要一致；拒绝 link/reparse point、WAL/journal、递归目标和已有目标。再校验 JSON/JSONL 与 SQLite integrity_check。失败副本保留调查，不能标记 VERIFIED。机器断电、后台未知写入者和多机不是保证范围。文件摘要不是加密签名；备份按本机审计数据管理。

恢复必须新目录，因此原数据保留；恢复后校验所有字节摘要和 SQLite。当前只做存储层完整性核验，不自动宣称全部业务引用及浏览器行为已恢复。独立 SUT DB、多数据库一致性和自动检测全部写入进程仍为后续项。

## R5-5.5 补充：显式拓扑与恢复语义校验

以上内容记录 R5-5.4 当时的实现边界，保留其历史口径。R5-5.5 将备份格式升级为 v2：计划须声明 `topology`。共享库继续使用 `database` 角色；独立库使用 `platform_database` 和 `teamflow_database` 两个角色。其余六个目录角色不变。v1 备份读取时按旧 shared 拓扑解释。

恢复检查现在可通过 `python scripts/restore_check.py --backup <备份目录> --work <全新检查目录>` 运行。它会在副本目录启动 Platform 与 TeamFlow，分别核对 schema / 拓扑、历史 Candidate / Case / Exploration / Chain / Run / Repair / Evidence 关系与 Blob 摘要，并经历史 API 读取后再跑一次真实浏览器业务流程。检查程序不会激活恢复副本。离线停机前提、`.env` 与密钥不属于角色备份、以及不提供在线一致性快照等限制仍然有效。详细结果见 [R5-5.5 多数据库离线备份与恢复验收报告](R5-5.5-B-多数据库离线备份与恢复验收报告.md)。
