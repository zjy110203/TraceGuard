# R5-5.5 C：Repair Generator 准入与接口决策包

状态：**设计准备 / 未批准 / 未由 R5-5.5 实现**。本文件只定义后续决策所需的边界、数据契约和验收方案。人工 Locator 编辑仍属于现有 Repair 工作流，不等于自动 Generator。

## 建议决策

只评估确定性 `locator_update`。在项目负责人批准可信语义映射来源、Evidence 新鲜度策略和接口契约以前，Generator 不得进入正式产品路径；不得生成 `wait_condition`、测试步骤、Assertion、Oracle 或产品代码修改。

### 可信映射

按信任强度排序：

1. **显式稳定语义键**：应用在控件上声明受控的组件键和元素键；映射记录由应用负责人随受控版本发布。
2. **受控版本映射表**：具名应用、旧/新应用版本、组件键、元素键、Locator、审批记录和映射文件摘要均明确绑定。
3. **浏览器观察**：DOM、文本相似度、邻近元素、位置或截图只能提供候选线索，不能单独建立语义身份。

语义键不得由 Generator 从标签文字或相似 DOM 临时推断。找不到受批准映射、应用版本无法确认或映射摘要不符时，返回 `NEEDS_HUMAN_INPUT`，不产生 Candidate。

## 数据流

```text
FAILED Run
  → 同一 Run 的受支持 Diagnosis hypothesis
  → 绑定的 locator_failure + 新鲜 DOM Evidence
  → 已批准的 app/version/semantic-key 映射
  → 唯一匹配检查
  → 只含 locator_update 的 DRAFT Candidate
  → 现有 Repair validate / submit / 人工 approve
  → 隔离 Sandbox Replay
  → 人工 Promotion（CAS）
  → Regression / 不可变 Rollback
```

Generator 建议 API 不得持有正式 TestCase 写入能力。所有后续阶段复用当前人工门禁和 CAS 事务。

## 输入契约草案

```json
{
  "case_id": "TC-...",
  "base_version": 3,
  "base_digest": "sha256:...",
  "source_run_id": "run_...",
  "hypothesis_id": "h-...",
  "evidence_refs": ["evd_locator_failure", "evd_dom_snapshot"],
  "semantic_mapping_id": "map_...",
  "semantic_mapping_sha256": "sha256:..."
}
```

服务端必须从正式存储重新读取 Case、Run、Diagnosis、Evidence 和映射；客户端提交的完整 Case、DOM、Evidence 内容和 `base_digest` 均不能作为权威事实。Diagnosis hypothesis 必须是该 Run 的 `SUPPORTED` 或 `CONFIRMED`，Evidence refs 必须是该 hypothesis 的 supporting 集合子集。

## Evidence 新鲜度与完整性

- `locator_failure` 与 DOM snapshot 必须来自同一个失败 Run、同一 step，并在生成输入中显式引用。
- DOM 采集时间、应用 origin/version、step ID、Evidence ID 和采集器版本都应可读取。
- 重新读取 Evidence 原始内容并重算 SHA-256；若内容存于 Blob，则校验 key、字节摘要和 Evidence `integrity_check` 一致。
- 最大证据年龄由项目负责人批准后进入有版本的 policy；没有批准值时保持未启用。旧 Run 的 Evidence 不因当前页面状态而变新。
- Evidence 缺失、损坏、跨 Run、跨 origin、超龄或版本不明均返回 `INCONCLUSIVE` / `NEEDS_HUMAN_INPUT`。

## 唯一性与不确定结果

候选 Locator 必须匹配恰好一个元素，并且元素语义键与批准映射完全相同：

| 匹配数 | 结果 |
|---:|---|
| 0 | `NEEDS_HUMAN_INPUT`，说明无匹配；不创建 Candidate |
| 1 | 可生成 DRAFT 建议，仍需现有人工审核 |
| 大于 1 | `AMBIGUOUS` / `NEEDS_HUMAN_INPUT`；不选第一个、不按排序挑选 |

超时、跨 frame 不可访问、DOM 观察不完整或摘要复核失败都不能降级为“最接近匹配”。

## 输出与保存契约

建议新增 append-only suggestion 记录，与正式 `cases/` 分开保存：

```json
{
  "suggestion_id": "rgs_...",
  "status": "DRAFT",
  "change_kinds": ["locator_update"],
  "base": {"case_id": "TC-...", "version": 3, "digest": "sha256:..."},
  "source": {"run_id": "run_...", "hypothesis_id": "h-...", "evidence_refs": ["..."]},
  "mapping": {"id": "map_...", "sha256": "sha256:...", "policy_version": "..."},
  "diff": [{"step_id": "s4", "before": "...", "after": "..."}],
  "uncertainty": [],
  "generator_version": "..."
}
```

保存前及用户接受建议时都重读 base Case 并复算 version/digest。并发改动时返回 `VERSION_CONFLICT`，不能把建议套到新版本。建议进入现有 Repair API 仍须验证 Assertion、Oracle、source refs 和 base digest。正式文件只能由已审批的 Promotion 事务写入。

## API 提案

候选形状为 `POST /api/v1/repairs/suggestions`。成功返回 DRAFT 预览和 suggestion ID；证据不足返回 `INCONCLUSIVE`；映射不存在返回 `NEEDS_HUMAN_INPUT`；多匹配返回 `AMBIGUOUS`；Case CAS 失败返回 `VERSION_CONFLICT`。建议对象只能通过显式操作送入现有 `/api/v1/repairs`；不得新增自动 approve、promote 或 rollback 路由。

实际路径和状态码仍待批准。本轮没有新增路由或持久化格式。

## 权限与安全

- Generator 仅由服务端调用；Agent、页面和浏览器不得接触 Eval token。
- 生成输入不能接受任意 URL、文件路径、SQL、Locator 回写路径或 app origin。
- 生成器只能读取 Case/Run/Diagnosis/Evidence 和批准的映射；不能写入正式 Case、GT、fault config 或 Oracle。
- `change_kinds` 必须严格等于 `{"locator_update"}`；candidate 除 Locator target 外，steps、required assertions、Oracle bindings、cleanup 和数据引用均须与 base 保持不变。
- Generator 无人工审批身份；`approved_by`、Promotion operator 和 rollback operator 必须来自现有人工审计字段与门禁。

## 准入测试矩阵

| 场景 | 预期 |
|---|---|
| 同 Run、同 step、受支持 hypothesis、可信映射、唯一元素 | 仅生成 DRAFT Locator 候选 |
| 无映射或 app/version 不受信任 | 无 Candidate，`NEEDS_HUMAN_INPUT` |
| 0 个或多个 DOM 匹配 | 无 Candidate，不猜测 |
| 错误 Run、错误 hypothesis、非 supporting ref | 拒绝 |
| Evidence 缺失、超龄、摘要不符、Blob 缺失 | 不确定/拒绝；无写入 |
| base version/digest 并发变化 | CAS 冲突；正式文件不变 |
| 删除/降低 Assertion 或改 Oracle | 拒绝 |
| DRAFT 未审批调用 Sandbox / Promotion | 拒绝 |
| 人工批准后基线失败、候选通过、control 回归通过 | 允许走现有 Promotion 门禁 |
| 重启 / 中断 / 重复提交 | 记录不可变；仅已有 Candidate transaction 恢复 |
