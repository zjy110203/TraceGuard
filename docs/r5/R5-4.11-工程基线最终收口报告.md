## 2. 超时分类：从"一律 BLOCKED"到"默认 FAIL"

### 2.1 缺陷与复现

旧代码：

```python
except subprocess.TimeoutExpired:
    return _exception_result(..., evidence=f"timeout after {step.timeout_s}s")  # -> blocked_evidence
```

`StepResult.status` 见 `blocked_evidence` 非空即返回 `BLOCKED`，因此**任何**超时都被判为"环境阻塞"。
复现即 `tests/test_verify_gate_timeout.py::test_command_timeout_is_fail_not_blocked`（修复前该用例会得到 BLOCKED）。

### 2.2 修改

- `Step.timeout_block_re`：步骤可声明"这个挂起能证明外部阻塞"的窄签名（默认空 = 无）。
- 改用 `Popen` + `communicate(timeout=)`，超时后 `taskkill /F /T`（Windows）/ `killpg`（POSIX）杀**整棵进程树**，
  再以 30 s 上限收尾，避免 runner 自己被挂住。
- `StepResult` 新增 `timed_out` / `timeout_s` / `output_tail`，日志记录 `TIMEOUT after Ns pid=<pid> killed=...` 与超时前输出。
- 退出码固定 124；`report.json` / `report.md`（新增 timeout 列）/ 控制台（`timeout=Ns`）/ 退出码四处一致。
- 超时不影响剩余门禁的 `NOT_RUN` 记录（`run_queue` 抽出后可直接测试）。
- 浏览器门禁补 1800 s 上限，超时同样记 FAIL 并保留已产生的输出。

### 2.3 回归

`tests/test_verify_gate_timeout.py`：**7 passed**（真实启动会挂起的子进程，不 mock 超时路径）

- 命令类超时 → FAIL，`timed_out=True`，`exit=124`，`blocked_evidence=""`
- 测试类超时 → FAIL（不是 EMPTY/SKIP）
- 超时记录秒数、pid、日志位置，且日志保留超时前输出
- 只有声明了 `timeout_block_re` 且命中 → BLOCKED
- 超时后剩余门禁仍记 NOT_RUN；`--keep-going` 时继续执行
- 控制台 / JSON / Markdown / 退出码一致

## 3. 测试库隔离：标记不能替代位置

### 3.1 缺陷

`_is_marked_test_db()` 把 `TRACEGUARD_TEST_DB=1` 当成充分条件，于是
`DATABASE_URL=sqlite:///D:/业务数据/business.db` + 该标记 → 直接沿用，测试会往真实业务库写表。

### 3.2 修改

- 新增 `_test_db_location(url)`：只接受系统临时目录与仓库 `.traceguard-tmp/`，`resolve()` 后判断（软链接无法绕）。
- `TRACEGUARD_TEST_DB=1` 只记录不授权；被它"放行"的路径会被覆盖，并在 `reason` 里写明"标记不能替代位置检查"。
- `DATABASE_URL` 与 `TRACEGUARD_DATABASE_URL` 不一致 → **两个都不用**，记录 `mismatch=true` 并 warn，改用会话临时库。
- 拒绝 Windows 盘符相对路径（`C:foo.db`，语义是"当前目录"而非 `C:\foo.db`）。
- `is_safe_test_db_url` 增加 `os.path.samefile` 检测：硬链接与正式库同 inode 时拒绝（路径看起来完全无关）。
- 会话诊断新增 `test_db_marker` / `mismatch` / `location_reason`，便于事后归因。

### 3.3 回归

`tests/test_db_isolation.py`：**18 passed / 1 skipped**

- 标记 + 业务路径 → 子进程仍被覆盖（真实子 pytest，非单测假象）
- 两个 URL 不一致 → 都不沿用 + 输出含 "different databases"
- 盘符相对路径拒绝；`data/../data/traceguard.db` 与 `./data/...` 路径穿越拒绝
- 硬链接到正式库拒绝（同盘创建，实测通过）
- 软链接测试：本机无符号链接权限（`WinError 1314`），**如实 skip 并附错误原文**，不伪装通过
- 正式库在"声称是测试库"的子进程中指纹（size/mtime_ns/sha256）前后一致

## 5. C04 `cleanup` 决策（D-R5-411-3）

调研结论：

- C04 状态为 `draft`（`registry.json`），README 明确"只有评审通过才置 frozen"，因此不属于"冻结契约"。
- `RunReport.cleanup` 是**可选**增量属性，`required` 未变；旧 payload 仍通过新 schema。
- 真实消费者只有三处（`apps/api/workbench.py`、`apps/api/chain_api.py`、前端），**没有外部/持久化严格校验**。
- 但 C04 顶层 `additionalProperties: false`：持有旧 schema 缓存的严格校验器会拒绝新 payload。

决策：**保留该字段并登记为增量候选**，同时用测试固定兼容包线，不擅自升版本号（draft 的版本号变更没有治理含义）：

1. 新 payload（含 cleanup）通过；
2. 旧 payload（无 cleanup）通过；
3. `cleanup` 不在 `required`；
4. 未知顶层字段仍被拒（证明严格性是真实存在的风险，而非想象）；
5. 用"删掉 cleanup 属性的旧 schema"复现旧校验器拒绝行为 —— 承认这是**残留风险**；
6. C05 未被污染（事件契约不含 cleanup）；
7. cleanup 里不得出现业务 verdict 字段（两个维度不可合并）。

测试：`tests/test_contract_compat_c04.py` **7 passed**。替代方案（把清理状态只放事件里）记录在 decisions 中，未采用的原因是
UI 需要按 Run 展示资源清理结果，走事件要做二次聚合且事件本身有保留窗口。
