## 2. 逐项根因与修复

### P0-1 CI workflow
- **根因**：第 94 行 `name:` 与 `runs-on:` 被写成同一行，YAML 解析为该 job 缺少 `runs-on`；push 触发分支列表不含开发分支。
- **修复**：拆成两个独立字段；push 加入 `r5-5-product-completion`；保留全部 Python/安全/产品 E2E/浏览器门禁。
- **验证**：本地 YAML 解析通过、5 个 job 均有合法 `runs-on`；远程实跑见 §3.7。

### P0-2 持久化降级序号冲突
- **根因**：`_next_sequence()` 写库成功用 `stream_seq`、失败回退本地 `_sequence`，两个号段落入同一空间。恢复后新事件复用了失败期已发事件的号；SSE 客户端按序号去重会静默跳过真实事件。
- **修复**：分离「事件身份/投递顺序」（`event_id` + `delivery_seq`）与「持久化恢复游标」（`v2:<stream_seq>:<instance>`）。`sequence=None` 表示未落库，不发 `id:` 行；前端按 `event_id` 去重。`strict` 失败直接抛错且不推进投递序；`degrade` 投递照常并标记不可回溯，恢复后 durability 状态返回 durable 但保留缺口区间。
- **验证**：`tests/test_sequence_faults.py` 故障注入；严格模式与降级模式分别验证；见 §3.2。

### P1-1 v2 游标身份校验
- **根因**：`resolve()` 仅解析 `stream_seq`，不校验 `producer_instance_id`；跨库位置相同即被误判有效。
- **修复**：七步校验（格式→实例归属→水位→越界→位置实例绑定→存在性→通过），`reason` 稳定子码；合法历史实例仍接受，不要求等于当前进程实例。
- **验证**：`tests/test_cursor_identity.py` 7 类矩阵；见 §3.2。

### P1-2 SSE 游标协议统一
- **根因**：设计文档 §7 描述「发送端不变 id=event_id、v2 为 4 段」，与实际代码（3 段 v2 游标、未持久化无 id）不符。
- **修复**：设计文档 §7 重写为唯一权威协议，明确持久化模式/内存模式 ID、旧 event_id 兼容、四类 notice、重启续接；状态由「待实施验收」改为真实实施状态，未完成事项保留在 §19/§20。实施报告 §2/§6 同步。
- **验证**：文档与代码逐字段核对（§7.2 表格对应 `cursor_token()`/`_sse()`）。

### P1-3 场景真实浏览器回归
- **根因**：project-query、page-navigation 只在注册表登记，无真实浏览器执行证据；project-query 选择器匹配多个项目会 strict-mode 失败；target 含动态 id 无法匹配。
- **修复**：两个场景走同一 `Explorer` 核心代码，在独立 TeamFlow 实例（独立 SQLite）上真实执行；选择器取首行；目标路径支持单段通配且编译准入与 goal 评估共用同一匹配规则；新增动态偏离测试（插入登出动作 → `POLICY_STOP`，不产生 VERIFIED Candidate）。
- **验证**：`tests/test_agentic_scenarios.py` 4 项新增全部通过真实 Chrome；见 §3.5。

### P1-4 C04 cleanup 兼容
- **根因**：C04 顶层 `additionalProperties: false`，缓存旧 schema 的严格校验器会拒绝带 `cleanup` 的新 payload。
- **修复**：决策 D-R5-411-3 收口——保持增量可选字段，不改 C05、不引入版本协商；明确宽松/新严格/旧严格三类消费者的操作口径，旧严格消费者须刷新 schema 缓存，禁止改判或降低断言。
- **验证**：`tests/test_contract_compat_c04.py` 8 项（新 payload 合法、旧 payload 仍合法、cleanup 非 required、顶层严格性未削弱、旧校验器拒绝被固化为已知风险、C05 零改动、cleanup 不携带 verdict）；见 §3.3。

### 3.1 Python 门禁 2 项失败的根因判定（不改判）

失败用例：`test_sandbox_paths.py::test_junction_to_victim_inside_root_is_not_deleted`、
`test_junction_pointing_outside_root_is_refused`。失败信息来自 WorkBuddy 运行时注入的
`sitecustomize.py`，为 `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50,"scope":"turn"}`，
即**沙箱在单个 turn 内累计删除达到 50 文件阈值时的保护**，不是项目断言失败。

证据链：
1. 安全门禁（`security/report.json`）中同一文件 `test_sandbox_paths.py` **PASS**（92 passed 含该文件）。
2. 单独重跑 `tests/test_sandbox_paths.py`：**8 passed**（`recheck-sandbox` basetemp）。
3. 两次独立全量复验失败的 junction 用例不同（一次 2 项、一次 1 项），说明是 turn 级计数偶发，与代码无关。
4. 按工作区约定拆成 7 个独立会话分段跑全量：**625 passed + 1 skipped**，覆盖全部 626 个收集用例，全绿。
5. 两次全量复验中一次为 625 passed + 1 skipped（`pytest-recheck-console.log`、`seg-basetemp-00` 那次全量）。

**处置**：主门禁 FAIL 按原始日志如实保留，不改判为 BLOCKED/PASS，不删断言、不调阈值；分段复验作为代码层补充证据一并归档。
