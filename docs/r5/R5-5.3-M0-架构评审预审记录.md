### 3.3 架构评审结论

职责边界本身是**清晰的**，且四条禁令都有代码支撑——这一点比多数设计文档阶段的项目更扎实。但必须指出两个"边界之外的缺口"，它们不在组件职责内，而在**组件被谁调用**这一层：

1. 组件之间的信任关系成立（Agent → Gateway → Browser 的单通道），但**平台 API 对调用方的信任是无条件的**（见 §5.4 / N1）。职责边界画在系统内部，画不到系统边缘。

### 4.1 Registry 的规范加载路径（关键澄清）

这一条必须写在最前面，因为它直接影响评审人读哪份文件。

```text
packages/contracts/loader.py:23-26
    CONTRACT_DIR = Path(__file__).resolve().parent
    SCHEMA_DIR   = CONTRACT_DIR / "schemas"        # ← 活动目录
    REGISTRY_FILE = CONTRACT_DIR / "registry.json"

packages/contracts/loader.py:76-79

        raise FileNotFoundError(f"schema declared but missing: {path}")
```

**结论【码证】**：Registry 的规范加载路径是 `packages/contracts/schemas/<schema_file>`。
`packages/contracts/` 根目录下同名文件**不参与加载**，任何机制（测试、服务、校验）都读不到它们。

### 4.2 影子副本已发生内容漂移（新发现 N5）

任务书要求"不要误把根目录重复文件当成活动 Schema"。核查后发现的问题比"重复"更严重——**两份内容不同**：

| 项 | 根目录副本（影子） | `schemas/`（活动） |
|---|---|---|
| 路径 | `packages/contracts/C05_Event.schema.json` | `packages/contracts/schemas/C05_Event.schema.json` |
| 大小 / 时间 | 1895 B / Nov 21 23:29 | 1809 B / Nov 24 17:19 |
| `$id` | `.../contracts/C05_Event.schema.json` | `.../contracts/C05/0.2.0-draft` |
| 顶层结构 | 扁平 `properties` | `$ref: #/$defs/EventEnvelope` |
| 必填字段 | `context_refs`、`observed_at`、`sequence`… | `run_id`、`step_id`、`recorded_at`、`sequence`… |
| 时间字段 | `observed_at` | `recorded_at` |
| 上下文 | `context_refs`（含 `workspace_id`/`project_id`/`run_id`…） | 顶层 `run_id` + `step_id` |
| 标题 | `C05 Event Envelope — DRAFT (stage 4 illustrative, NOT frozen)` | `Event`，`status: draft` |

同一现象存在于 C06 / C11 / C12（逐对比 `diff` 均为 DIFFERENT）。

这不是排版差异，是**两代字段模型**。风险很具体：评审人若打开根目录那份，会基于 `context_refs`/`observed_at` 讨论契约，而实现用的是 `run_id`/`step_id`/`recorded_at`，**审的和做的不是同一个东西**。

> 处置建议（不在本轮执行）：由负责人裁定后，将根目录副本删除或移入 `docs/` 归档，并加一条测试断言"根目录不得存在 `C*.schema.json`"。本轮仅登记，不动文件。

## 5. 安全与权限评审

本节是本次预审的重点。任务书要求"形成明确结论：当前人工审核机制能提供哪些保证、不能提供哪些保证"。为避免结论含混，先给事实，再给能力矩阵。

### 5.1 Candidate 审批链的事实核查

**（1）reviewer 由请求方自行填写 —— 是**

```text
apps/api/candidate_api.py:278-286
    class ReviewRequest(BaseModel):
        reviewer: str                  # ← 请求体自由文本
        approval_record: str = ""
        reason: str = ""
        review_confirmed: list[str] = []
        uncertainty_acknowledged: bool = False

apps/api/candidate_api.py:370-373
    if not body.reviewer.strip():
        raise ValidationError("reviewer is required to approve a candidate")
```

校验只有 `strip()`（非空）。**任意外部调用方可填入任意人名**，服务端不做任何身份核验。`approval_record` 同理，是自由文本，不与任何工单系统绑定校验。

**（2）`reviewer_is_local_audit_field` 的真实含义 —— 是自我声明，不是控制项**

```text
apps/api/candidate_api.py:485-487
    # reviewer is a local audit field: no identity module exists yet,
    # so the record never claims authenticated identity.
    "reviewer_is_local_audit_field": True,
```

三处硬编码为常量 `True`：编译时 `:362`、批准时 `:487`、拒绝时 `:517`。

**真实含义**：它是一个**诚实的否定性声明**——"本字段不是已认证身份，记录不得被当作身份凭证"。它做得对的地方在于不冒充认证（这正是安全文化上的加分项）；但它**作为审计判据没有区分力**：所有记录恒为 `True`，无法用它将"可信审批"与"任意署名审批"分开。换言之，它保护的是"记录不撒谎"，不保护"记录是真的"。

**（3）Candidate 是否有服务端身份认证 —— 没有**

| 核查点 | 结果 |
|---|---|
| `apps/api/main.py:47` 中间件 | 仅 `RequestIdMiddleware`（请求追踪），**无认证中间件** |
| 全量路由 `Depends` 使用 | `apps/api/*.py` 中**无** `get_current_user` / `Bearer` / API-Key 入站校验 |
| 唯一 token 出现处 | `apps/api/extensions.py:130` `app.state.eval_token` → 作为 `X-Eval-Token` **出站**发给 SUT（`:135`），是客户端凭证，**不是**入站用户认证 |
| 对比：SUT 侧 | `apps/teamflow/api.py:34-40` 反而有 `current_user`（cookie 会话，`:34-40` 注释自承"Demo auth… Production must use signed tokens + password hashing"） |

**这是一个值得注意的反差**：作为被测系统的 TeamFlow 有（哪怕是 demo 的）身份机制，而作为平台的 TraceGuard API 一个都没有。平台的审批门禁建立在"调用方自觉"之上。

**（4）Candidate 侧**确实存在**真实的服务端完整性门禁**（必须公平记录，不能只讲缺口）：

| 门禁 | 位置 | 性质 |
|---|---|---|

### 5.4 能力矩阵：能保证什么，不能保证什么

**当前人工审核机制能够保证：**

1. **流程不可跳过**——不存在"直接生成正式用例"的路径，编译只产出 `PENDING_REVIEW`，写正式库仅发生在 `approve`（`candidate_api.py:465-473`）。
2. **材料不可篡改**——审批时重算溯源、重跑编译校验、比对 trace hash（`candidate_api.py:425-442`）。
3. **确认不可含糊**——必需清单项逐项确认、不确定性笔记单独确认、未知项拒绝（`:392-419`）。
4. **重复不可发生**——单次审批、正式用例 append-only、同一 trace 重编译不得覆盖已审结论（`:341-350`、`:467-471`）。
5. **模型不可自裁**——Oracle 在编译期恒为 `approved=False`（`compiler.py:712`），只有人工审批才翻转（`candidate_api.py:448-461`）。
6. **Agent 不可自批**——API 层拒绝 6 类自批署名（`extensions.py:41,417`）。
7. **GT 不可达**——Ground Truth 不挂 `app.state`（`extensions.py:469-473`）。

**当前人工审核机制不能保证：**

1. **不能保证"签字者是人"**——任何能连到 API 的进程都可自称任意人名。
2. **不能保证"签字者有权限"**——无角色，无授权矩阵，谁都能批。
3. **不能保证"签字不可否认"**——无身份绑定，事后无法证明是谁做的决定。
4. **不能保证多用户环境下的责任隔离**——所有审批共享同一无认证入口。
5. **不能保证远程部署安全**——一旦监听 `0.0.0.0` 或置于反向代理后，审批门禁等价于"谁都能点"。
6. **不能保证 Repair 拒绝可追溯**——reject 分支无操作者（N4）。
7. **不能保证自批拦截一致**——Service 层仅拦小写 `agent`（N2）。

**一句话结论**：当前机制是**"单人本地可信环境下的防误操作机制"**，不是**"多人/远程环境下的审批授权机制"**。前者它做得很好，后者它明确没有做——而且代码注释（`candidate_api.py:485-486`）诚实地承认了这一点，这一点应当被肯定，不应被当成隐瞒。

**建议（本轮不实施）**：在多用户或远程部署**之前**引入服务端认证身份 + RBAC，最低要求为：审批主体来自经验证的会话而非请求体、审批动作绑定角色（如 `qa-lead` 可批 Candidate、安全负责人可批破坏性场景）、审批记录含不可否认的审计标识。该项建议登记为 M1 的前置条件，**不构成本轮代码变更**。

## 9. O1～O4 技术观察项及推荐方案

四项均为 **🟡 OPEN-REVIEW** 状态，来源 DR2 记录 §14.10。以下给出推荐方案、理由、实施阶段、验收条件。**均为建议，未批准、未实现。**

### O1 Scenario Digest 算法标识

| 项 | 内容 |
|---|---|
| 问题 | 读到未知 `digest_algorithm`（如 `canonical-json-v2` 或伪造值）时，硬拒绝还是降级？ |
| **推荐方案** | **硬拒绝，禁止静默回退**。注册期未知算法 → `ValueError`（注册失败）；读取期复算遇未知算法 → 错误码 `unsupported-digest-algorithm`，判定为不可验证而非"按当前算法重算" |
| 理由 | 静默回退会让 `scenario_digest` 的校验结论**不可信**：同一份内容在不同版本下算出不同摘要，却都被判"通过"，历史身份保障就失效了。Digest 的价值全在"同一算法同一结果"，一旦允许回退，等于把身份校验降级为"看起来像通过" |
| 历史算法处理 | **不迁移**。记录侧保存 `digest_algorithm` 与 `digest_algorithm_version` 两个字段，读取时按记录自带算法复算；算法不在白名单 → 拒绝，**不得改写历史记录去迎合新算法** |
| 实施阶段 | M1（与 Scenario 注册同期，属契约层） |
| 验收条件 | ① 未知算法注册被拒且有错误码；② 未知算法读取返回 `unsupported-digest-algorithm` 而非重算；③ 历史 v1 记录可读且结论不变；④ 用例覆盖"伪造算法名"与"跨版本读取"两类 |

### O2 Execution Lock 的作用域与崩溃恢复

| 项 | 内容 |
|---|---|
| 问题 | 锁的跨进程范围、Worker 互斥、崩溃回收、fencing 是否需要 |
| **推荐方案** | **首期明确为单进程部署**：进程内 `run_id → 共享 Run 锁`，覆盖该进程内**全部 Worker**（Worker 是线程，不是进程）；同一 Run 的 `verify→execute` 区间由这把锁串行化。**多进程部署前必须补齐** DB Lease + fencing token + 启动扫描回收，否则不得扩容 |
| 理由 | 当前架构是单机单进程 + 线程 Worker（`apps/api/main.py:107` `max_workers`），进程内锁足以保证互斥。若首期就上 DB 锁，会把 M1 的复杂度推到分布式一致性上，而这一阶段的真实风险是"单机并发写同一 Run"，不是"跨机房" |
| 边界写法 | 把边界**写死在部署拓扑上**：文档明示"单进程；多进程 = 需要重新评审 O2"。这样锁的实现范围与部署形态一一对应，避免"代码是线程锁、部署却开了多副本"的默认错配 |
| 崩溃恢复 | 单进程场景用租约超时（与 D4 参数联动）；进程崩溃时锁随进程消失，无需显式释放。**多进程场景**才需要 lease + fence |
| 实施阶段 | M1（单进程锁）；多进程支持列为 M2 后独立评审项 |
| 验收条件 | ① 同一 `run_id` 并发两个 Action，验证者之一必须被阻塞（测试可证）；② Worker 数 >1 时仍满足互斥；③ 文档明确"多进程未支持"且服务在多副本配置下启动即拒或显式告警；④ D4 参数变更能影响租约超时 |

### O3 `url_and_content` 的归类与计数口径

| 项 | 内容 |
|---|---|
| 问题 | 当作 evaluator kind（+9，共 20 种，27 组），还是当作纯语法糖宏（+8，共 19 种，24 组） |
| **推荐方案** | **纯语法糖**：注册阶段展开为 `all_of`，**不进入 `SUPPORTED_KINDS`** |
| 理由 | 它的语义完全等价于"url 断言 ∧ content 断言"的合取，没有独立求值逻辑。把它放进 `SUPPORTED_KINDS` 会造成两处实现同一语义（宏展开 + kind 求值），长期必然分叉；而已有 `all_of` 能精确表达该语义，复用比新增更安全 |
| 需同步明确的三个数字 | ① **evaluator kind**：11 + 8 = **19 种**（`url_and_content` 不计入）；② **声明形式**：19 + 1 宏 = **20 种**（对外呈现不变，作者仍可写 `url_and_content`）；③ **参数化测试组**：**24 组**（原 27 组 − 3 组，宏展开的正确性由 `all_of` 组合测试覆盖） |
| 连带修正点 | 注册期 kind 合法性校验的判定集必须是 19 项；若校验集仍为 20 项，会出现"注册期接受、求值期无 handler"的空洞。验收矩阵 §3.1 / §3.2 / §6.1 三处数字须一并改 |
| 实施阶段 | M2（断言体系落地前定稿） |
| 验收条件 | ① `url_and_content` 不出现在 `SUPPORTED_KINDS`；② 注册期展开为 `all_of` 且展开结果可断言；③ 19 / 20 / 24 三个数字在设计与矩阵中一致；④ 参数化测试组数与矩阵声明数**逐一对齐**（不留"声明 24、实跑 26"这类漂移） |

|---|---|
| 问题 | DeepSeek / OpenAI 各自的默认模型名、版本固定策略、Key/base_url/模型名三者绑定校验 |
| **推荐方案** | 显式声明 **Provider → Endpoint → Model** 三元组绑定，并**拒绝跨 Provider 混搭**：`provider=deepseek` 只接受 `https://api.deepseek.com/v1` + `deepseek-*` 模型名；`provider=openai` 只接受 `https://api.openai.com/v1` + `gpt-*`/`o*` 模型名。三元组任一不匹配 → **启动期拒绝**（配置错误不该拖到调用期才暴露） |
| 理由 | 混搭的典型事故是"换了 Key 和 base_url，却继续用上一个 Provider 的模型名"，请求会以 4xx 或更糟——被网关静默改写成另一个模型——失败。后者会污染成本台账与模型版本记录，使"记录实际返回的模型名"失去意义。启动期拒绝把这类事故前移到部署时 |
| 别名漂移 | 首期**禁止 alias 漂移**：配置文件写固定快照名（如 `deepseek-chat-<date>` 形式），不使用 `latest`。若 Provider 侧强制漂移，则必须在 Trace 中记录**实际返回的模型名**（D8 已要求），二者取交集 |
| 实施阶段 | **M4 实施前完成**，不提前接入真实模型 |
| 验收条件 | ① 三元组不匹配时服务启动失败并给出明确错误；② 拒绝 `latest` 类别名；③ 运行时记录实际模型名；④ 该逻辑有单元测试但**不发起真实网络请求**（用 mock） |

**四项的共同纪律**：O1～O4 的推荐方案**不改变任何既有决策、不代表任何实现、不解除 D8、不批准 D1～D5**。评审若采纳，需回写 §10 或对应设计章节，并在验收矩阵登记新准入项。
