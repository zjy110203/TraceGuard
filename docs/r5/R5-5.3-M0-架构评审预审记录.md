### 3.3 架构评审结论

职责边界本身是**清晰的**，且四条禁令都有代码支撑——这一点比多数设计文档阶段的项目更扎实。但必须指出两个"边界之外的缺口"，它们不在组件职责内，而在**组件被谁调用**这一层：

1. 组件之间的信任关系成立（Agent → Gateway → Browser 的单通道），但**平台 API 对调用方的信任是无条件的**（见 §5.4 / N1）；而且**同一条"不得自批"禁令只覆盖了 Repair，没覆盖 Candidate**（见 §5.5 / N8）。
2. Trace 的算法版本停在 v2，设计已写到 v3（见 §4.5）。这不是职责问题，但会影响"可追溯"这一条的强度声明；v3 的实施固定在 M3-7，不得前移。

**架构维度结论：技术架构可进入评审，但"人工审批是可信边界"这一前提尚不成立，构成 M0 冻结阻塞项。**

### 4.1 Registry 的规范加载路径（关键澄清）

这一条必须写在最前面，因为它直接影响评审人读哪份文件。

```text
packages/contracts/loader.py:23-26
    CONTRACT_DIR = Path(__file__).resolve().parent
    SCHEMA_DIR   = CONTRACT_DIR / "schemas"        # ← 活动目录
    REGISTRY_FILE = CONTRACT_DIR / "registry.json"

packages/contracts/loader.py:76-79
    path = schema_dir / fname                      # ← 只拼 schemas/
    if not path.exists():
        raise FileNotFoundError(f"schema declared but missing: {path}")
```

**结论【码证】**：Registry 的规范加载路径是 `packages/contracts/schemas/<schema_file>`。
`packages/contracts/` 根目录下同名文件**不参与加载**，任何机制（测试、服务、校验）都读不到它们。

### 4.2 影子副本已发生内容漂移（新发现 N5）

任务书要求"不要误把根目录重复文件当成活动 Schema"。核查后发现的问题比"重复"更严重——**两份内容不同**：

| 项 | 根目录副本（影子） | `schemas/`（活动） |
|---|---|---|
| 路径 | `packages/contracts/C05_Event.schema.json` | `packages/contracts/schemas/C05_Event.schema.json` |
| 大小 / 时间 | 1895 B / Nov 21 23:29 | 1809 B / Nov 24 17:19 |
| `$id` | `.../contracts/C05_Event.schema.json` | `.../contracts/C05/0.2.0-draft` |
| 顶层结构 | 扁平 `properties` | `$ref: #/$defs/EventEnvelope` |
| 必填字段 | `context_refs`、`observed_at`、`sequence`… | `run_id`、`step_id`、`recorded_at`、`sequence`… |
| 时间字段 | `observed_at` | `recorded_at` |
| 上下文 | `context_refs`（含 `workspace_id`/`project_id`/`run_id`…） | 顶层 `run_id` + `step_id` |
| 标题 | `C05 Event Envelope — DRAFT (stage 4 illustrative, NOT frozen)` | `Event`，`status: draft` |

同一现象存在于 C06 / C11 / C12（逐对比 `diff` 均为 DIFFERENT）。

这不是排版差异，是**两代字段模型**。风险很具体：评审人若打开根目录那份，会基于 `context_refs`/`observed_at` 讨论契约，而实现用的是 `run_id`/`step_id`/`recorded_at`，**审的和做的不是同一个东西**。

判定不靠"看起来像"，靠**加载路径**与**引用面**两条证据：


引用面检索结果（`grep "contracts/C05_Event\|contracts/C06_Evidence\|contracts/C11_Repair\|contracts/C12_Benchmark"`）：

| 引用位置 | 性质 | 影响 |

### 4.3 C05 冻结状态的三层口径不一致（新发现 N6）

任务书要求区分"A. 阶段内不允许修改"与"B. 已正式评审并标记 frozen"。核查结果：**当前仓库同时存在三种口径，且互不吻合**。

|---|---|---|---|
| 设计文档 | `R5-5.3-总体设计与实施规格.md:37` | "**不修改 C05 冻结契约**（`packages/contracts/schemas/C05_Event.schema.json` 零改动）" | 被称为**冻结契约** |
| 设计文档 | `R5-5.3-接口与数据契约台账.md:735` | "**冻结承诺**：`.../C05_Event.schema.json` 零改动" | 被称为**冻结承诺** |
| 治理元数据 | `packages/contracts/registry.json` → C05 | `"version": "0.2.0-draft"`, `"status": "draft"`, `"owner_role": "待分配"` | **draft** |
| 治理说明 | `packages/contracts/README.md:15` | C05 冻结状态列 = "**待冻结**" | **待冻结** |

**这一差异不由本轮裁定**，按任务书要求如实上报，等待负责人确认正式口径。三种可选口径及其后果：

**结论性约束（写入 §13.2 冻结条件与本记录 §11）**：

1. **M1、M2 一律保持 `HASH_VERSION = 2`**，不得新增 v3 常量、不得新增 v3 分支、不得把 `scenario_id/version/digest` 并入 v2 字段集。

3. v3 实现的唯一入口是 **M3-7**；实施前须同时满足：`decision_id`/`proposed_action`/`policy_decision`/`decision_source` 已有稳定产出（M3-2/M3-6），且 O1 Digest 算法已获批（M1 阶段）。
4. v1/v2 记录**不迁移、不改写、不重签**；读取按 `hash_version` 分派，三版本并存。

同时注意 `tests/test_trace_integrity_v2.py:132,138` 中出现的 `"GOAL_REACHED"` 只是被当作**字符串载荷**用于构造历史 hash 用例，不代表 `StopReason` 含该值——`tests/test_goal_semantics.py:170` 恰恰断言 `GOAL_REACHED` **不在** `StopReason` 中，二者不矛盾。

### 5.1 Candidate 审批链的事实核查

**（2）`reviewer_is_local_audit_field` 的真实含义 —— 是自我声明，不是控制项**

**（3）Candidate 是否有服务端身份认证 —— 没有**

### 5.2 Repair 审批链的事实核查

**SELF_APPROVERS 是纯字符串过滤 —— 是，而且两层口径不一致（N2）**

| 层 | 拦截集合 | 大小写 | 绕过难度 |
|---|---|---|---|
| API（`extensions.py:41`） | `{"", agent, ai, system, auto, traceguard}` | `strip().lower()` 后比较 | 换个词即可（如 `robot`、`agent1`、`Agent `→被拦、`ai-bot`→放行） |
| Service（`repair.py:252`） | `{"agent"}` | **区分大小写等值** | `"Agent"`、`"AI"`、`"System"`、`"Auto"`、`"TraceGuard"` **全部放行** |

**风险落点**：凡不经过 HTTP 层的调用——内部脚本、未来 Worker 进程、单元/集成测试、乃至 M2 之后新增的任何服务内调用路径——**只受 Service 层约束**，而该层只认小写 `agent`。这不是"能不能防住 AI"的语义问题，是**同一个安全策略在两处实现对不上**的工程缺陷。

**Repair 拒绝分支丢弃操作者（N4，R1 表述校准）**

**先纠正首轮的一处过重表述**：首轮本文写"`reviewer` 默认值 `"human"` 会**伪造出一个操作者**"。复核源码后确认这**不准确**——该默认值只存在于 Pydantic 模型的缺省里，`reject_repair` 从未把它写进任何记录，因此**不存在"已持久化一个假的 human 身份"这件事**。准确的问题只有两条：默认值本身是坏味道（读代码的人会误以为操作者已被采集），以及拒绝操作**根本没有操作者字段**。

```text
apps/api/extensions.py:397-399
    class RejectBody(BaseModel):
        reason: str
        reviewer: str = "human"        # 默认值给出一个人名，但下游不使用

apps/api/extensions.py:434-442
    def reject_repair(proposal_id: str, body: RejectBody, request: Request):
        if not body.reason.strip():
            raise ValidationError("rejection reason is required")
        ...
        proposal = service.reject(proposal_id, body.reason)   # body.reviewer 从未传入

packages/execution/repair.py:259-264
    def reject(self, proposal_id: str, reason: str) -> RepairProposal:
        with self._lock:
            p = self._get(proposal_id)
            self._transition(p, "REJECTED")
            p.failure_reason = reason[:500]
            return p                                          # 无 approver / reviewer 入参
```

| 事实 | 判断 | 证据强度 |
|---|---|---|
| `RejectBody.reviewer` 默认 `"human"` | **属实**，但这是"未被读取的默认值" | 码证 `extensions.py:399` |
| `reviewer` 是否被持久化 | **否**，全仓库无任何 `p.reviewer = ...` 或 `reviewed_by` 赋值 | 码证 `extensions.py:434-442`、`repair.py:259-264` |
| `service.reject()` 是否有操作者参数 | **否**，签名为 `(proposal_id, reason)` | 码证 `repair.py:259` |
| 拒绝后 `RepairProposal` 是否记录谁拒绝 | **否**；`approved_by` 仅由 `approve()` 写入（`repair.py:255`） | 码证 |
| 拒绝是否留时间戳 / 审计标识 | **否** | 码证 |
| 因此审计链在 reject 处断裂 | **成立** | — |
| 因此"已伪造 human 身份并落库" | **不成立**，首轮措辞作废 | — |

**准确的问题陈述**：`reject` 是**一次不留操作者的状态迁移**。它与 `approve` 不对称——批准的记录能回答"谁批的"，拒绝的记录只能回答"为什么拒"，不能回答"谁拒的"。在单人本地环境下这不影响使用；一旦进入"多用户 / 审计追责 / 合规留痕"场景，reject 就是审计链上唯一的断点。

**修复方向（M1 登记，本轮不改）**：`RejectBody` 去掉 `"human"` 默认值（改为必填），`reject_repair` 把 `reviewer` 透传，`RepairService.reject()` 增加 `*, reviewer: str` 并写入 `rejected_by` 字段；同时把"拒绝操作者必填"列入 N7 的补测范围。**注意**：透传的 `reviewer` 仍是请求体自由文本，其可信度问题由 N1/N8 覆盖，不能因为"补齐了字段"就认为审计可信。

### 5.4 能力矩阵：能保证什么，不能保证什么

任务书要求"区分内容完整性、操作流程和主体身份可信度"。这三者混在一张清单里是失真的根源：**内容完整性做得越好，越容易被误读成"审批可信"**。因此本节拆成三个维度分别给结论。

#### 维度一：内容完整性 —— 材料有没有被篡改、有没有缺项

| 门禁 | 位置 | 强度 |
|---|---|---|
| 必需清单项逐项确认，缺一项即 422 | `candidate_api.py:392-404` | 强（服务端强制） |
| 引用不存在的清单项即 422 | `:405-410` | 强 |
| 有不确定性笔记时须显式确认 | `:411-419` | 强 |
| 溯源复验：源探索仍存在、hash 仍匹配 | `:425-437` | 强 |
| Compiler 静态校验在审批时**重跑** | `:442` | 强 |
| 正式用例不可覆盖（append-only） | `:467-471` | 强 |
| 编译准入 `GoalStatus.VERIFIED` + 交叉比对 | `:584-605` | 强 |
| Repair 审批需 `approval_record` 非空 | `extensions.py:420-422` | 弱（仅非空） |

**结论：内容完整性维度是当前实现最扎实的部分，可以声称"材料不可静默篡改"。**

#### 维度二：操作流程 —— 流程能不能被跳过、能不能重复

| 门禁 | 位置 | 强度 |
|---|---|---|
| 不存在"直接写正式库"的路径（只产出 `PENDING_REVIEW`） | `candidate_api.py:341-350`、`:465-473` | 强 |
| 审批单次有效（非 PENDING 即 409/422） | `:379-383` | 强 |
| Oracle 编译期恒 `approved=False` | `compiler.py:712` | 强 |
| GT 不挂 `app.state`，无业务路由可达 | `extensions.py:469-473`、`:494-497` | 强 |
| 状态机迁移受 `_transition` 校验 | `repair.py:238-257` | 强 |

**结论：操作流程维度可以声称"流程不可跳过"。这是流程设计层面的保证，与"谁在操作"无关。**

#### 维度三：主体身份可信度 —— 签字的人是不是他声称的人

| 能力 | 现状 | 证据 |
|---|---|---|
| 入站身份认证 | **无** | `main.py:47` 仅 `RequestIdMiddleware` |
| 角色 / RBAC | **无** | 全仓无 role 判定（`grep -i rbac\|role` 仅命中测试字段） |
| 操作者与真实主体绑定 | **无** | `reviewer`/`approver` 来自请求体自由文本 |
| 审批不可否认（签名/时间戳/工单校验） | **无** | `approval_record` 不与任何外部系统校验 |
| 供应商自批拦截（Repair） | **有，但弱** | `extensions.py:41,417`（6 值黑名单）；`repair.py:252`（仅小写 `agent`） |
| 供应商自批拦截（Candidate） | **完全没有** | 见 §5.5 / **N8** |
| 审计判据可区分 | **无** | `reviewer_is_local_audit_field` 恒 `True`（N3） |

**结论：主体身份维度是空的。** 不是因为实现得不好，而是因为**这一维度尚无任何实现**。

#### 黑名单的定位（必须写清楚，否则会被当成认证）

`SELF_APPROVERS` 这类集合**不是身份认证**，它只是**防误操作的名字过滤**：

| 它能做 | 它不能做 |
|---|---|
| 拦住"顺手填 agent 就点了批准"的误操作 | 拦住一个自称 `zhangsan` 的进程 |
| 给审查者一个显式的意图信号（"这里不许自批"） | 证明 `zhangsan` 是张三 |
| 在无认证前提下提供最低限度的**声明性**约束 | 替代登录、会话、签名、RBAC 中的任何一项 |

把它当认证用，等于把"门上贴了'请勿入内'"当成"门锁"。因此本记录的统一口径是：**黑名单属于维度二的辅助措施（防误操作），不属于维度三（主体可信）。**

#### 汇总：当前机制的真实名字

| 维度 | 能力 | 可否对外声称 |
|---|---|---|
| 内容完整性 | 强 | ✅ "材料不可静默篡改" |
| 操作流程 | 强 | ✅ "流程不可跳过、不可重复" |
| 主体身份 | 无 | ❌ **不得声称"审批人可信"** |

**一句话结论（R1 修订）**：当前机制是**"单人本地可信环境下的防误操作 + 材料完整性校验机制"**。它在维度一、维度二做得很扎实，在维度三**一项都没有**——而且代码注释（`candidate_api.py:485-486`）诚实地承认了这一点，这一点应当被肯定，不应被当成隐瞒。

**建议（本轮不实施）**：在多用户或远程部署**之前**引入服务端认证身份 + RBAC，最低要求为：审批主体来自经验证会话而非请求体、审批动作绑定角色、审批记录含不可否认的审计标识。该项登记为 M1 的前置条件，**不构成本轮代码变更**。

### 5.5 Candidate 自审批缺口（新发现 N8）

首轮预审核了 Repair 侧黑名单，**漏核了 Candidate 侧**。R1 补齐后发现：Candidate 审批接口**没有任何自审批拒绝规则**。

```text
apps/api/candidate_api.py:368-373
    @router.post("/candidates/{candidate_id}/approve")
    def approve_candidate(request: Request, candidate_id: str, body: ReviewRequest) -> dict[str, Any]:
        if not body.reviewer.strip():
            raise ValidationError("reviewer is required to approve a candidate")
        if not body.approval_record.strip():
            raise ValidationError("approval_record is required to approve a candidate")
        # ← 到此为止。没有 SELF_APPROVERS 判定，没有 "agent"/"ai"/"system" 过滤。
```

对比三条链路，缺口一目了然：

| 接口 | 自审批拦截 | 证据 |
|---|---|---|
| Repair `approve` | **有**（6 值黑名单 + Service 层弱拦截） | `extensions.py:417`；`repair.py:252` |
| Candidate `approve` | **无**（仅要求非空） | `candidate_api.py:368-373` |
| Candidate `reject` | **无**（仅要求非空 + reason） | `candidate_api.py:495-502` |

**这说明什么**：同一个项目里，"不许 Agent 自批"这条禁令**在 Repair 上做了、在 Candidate 上没做**。而 Candidate 恰恰是**通往正式用例库的唯一入口**（`approve` 之后才写正式库），它比 Repair 更关键。所以这不是"少写一行"的问题，是**禁令覆盖不全**：把 `reviewer: "agent"` 填进 Candidate approve，服务端会照单全收，Candidate 直接转正式用例。

**为什么不能靠"补个黑名单"收工**——三层要分清，混起来就会得出错误结论：

| 层 | 补黑名单能否解决 | 说明 |
|---|---|---|
| 内容完整性 | 无关 | 黑名单不校验清单项，与本维度正交 |
| 操作流程 | **部分** | 黑名单能拦住"流程上不该由实现方按下批准"的误操作 |
| 主体身份可信度 | **完全不能** | 换任何名字（`robot`、`qa-bot`、`zhangsan`）都通过；无认证时名字无意义 |

**因此 N8 的正确处置是两条，缺一不可**：

1. **短期（M1）**：Candidate `approve`/`reject` 引入与 Repair 统一的自审批黑名单，两处合并为**单一共享常量 + 单一判定函数**（顺带修掉 N2 的两层口径不一致）；补测全部黑名单值在两条链路上均被拒（修 N7）。
2. **中期（M1 前置条件，随 N1）**：审批主体来自经验证会话。**只有第 2 条实现后，"审批可信"才是可声称的**；第 1 条只是让"误操作"不容易发生。

**必须避免的错误结论**：

- ❌ "Candidate 也加了黑名单，所以自审批问题解决了" —— 只解决了维度二的一小块。
- ❌ "清单确认已经很严格，所以 Agent 批不了" —— 清单确认是**内容**门禁，Agent 完全可以逐项确认后再批。
- ❌ "本地部署没人能连进来" —— 见 §5.6，`--host 0.0.0.0` 一个参数就能改变这个前提。

### 5.6 网络暴露边界（N1 取证细化）

首轮只证了"没有认证中间件"。但"没有认证"与"能否被远程访问"是两个问题，必须分别取证。

#### (1) 默认监听地址：loopback —— 是

```text
packages/core/config.py:63-64
    api_host: str = "127.0.0.1"
    api_port: int = 8000

scripts/serve.py:90
    parser.add_argument("--host", default="127.0.0.1")
```

默认值确实是 loopback，这一点设计意图是明确的。

#### (2) 但 `api_host` 配置项是**死配置**，实际监听由命令行参数决定

| 事实 | 证据 |
|---|---|
| `Settings.api_host` 在全仓库**除定义行外无任何读取点** | `grep -rn "api_host" --include=*.py` 仅命中 `config.py:63`（其余命中均为 `.traceguard-tmp/` 下的临时脚本） |
| 真正的监听地址来自 `scripts/serve.py --host` | `serve.py:90` 定义，`:75` 传给 `uvicorn.Config(app_path, host=host, ...)` |
| 该参数**无任何校验**，`0.0.0.0` 与任意 IP 均被接受 | `serve.py:90-95` 无取值约束 |

也就是说：改 `.env` 里的 `API_HOST` **不会**改变监听地址（读者会误以为受控），而 `--host 0.0.0.0` **会**立即把平台与 TeamFlow 一起暴露到所有网卡。

#### (3) 启动期没有任何"无认证 + 非 loopback"的阻断

```text
apps/api/main.py:44-47
    app = FastAPI(title="TraceGuard Platform API", version="0.1.0-m0", lifespan=lifespan)
    app.add_middleware(RequestIdMiddleware)      # 唯一中间件，无认证
```

- 无 host 白名单校验；
- 无"非 loopback 且无认证 → 拒绝启动"的检查；
- 无告警日志提示"当前监听在非本机地址"；
- `serve.py` 会把 SPA 与 API 一起暴露，并打印 `http://0.0.0.0:8000/` 的提示语，**读起来像是正常用法**。

#### (4) 首期部署边界的结论

| 项 | 结论 |
|---|---|
| 允许的部署形态 | **单用户、本机、单进程**（`127.0.0.1` / `localhost` / `::1`） |
| 当前是否强制该形态 | **否**——默认符合，但可被一个参数打开，且打开时无任何警示 |
| 远程/多用户部署的前提 | 服务端身份认证 + RBAC **必须先行**；在此之前不得把平台置于反向代理后或对外网卡监听 |
| 本地审核记录能否称为"可信远程审批" | **不能**。本地 `127.0.0.1` 上的审批记录，其可信度来自"这台机器只有我"，不是来自系统 |

**M1 必须落地的保护（登记为 M1-0，见验收矩阵）**：

1. 默认仅允许 `127.0.0.1` / `localhost` / `::1`；非 loopback 地址需**显式配置**才接受，否则启动即拒并给出可诊断错误。
2. `app_env=prod` 且未配置认证时，**拒绝启动**（fail-closed），不得以"先跑起来再说"的方式放行。
3. 移除 `api_host` 死配置，或让 `serve.py` 以它为准（二者取其一，不得两套并存）。
4. 监听在非 loopback 时，启动日志必须显式警示"当前无身份认证，审批门禁不可信"。
5. 上述行为需有**负向测试**（非 loopback 未授权 → 拒绝；prod 无认证 → 拒绝）。

**本轮不改代码**：以上全部为 M1 实施项，本轮仅登记与取证。

## 9. O1～O4 技术观察项及推荐方案

四项均为 **🟡 OPEN-REVIEW** 状态，来源 DR2 记录 §14.10。以下给出推荐方案、理由、实施阶段、验收条件。**均为建议，未批准、未实现。**

### O1 Scenario Digest 算法标识

| 项 | 内容 |
|---|---|
| 问题 | 读到未知 `digest_algorithm`（如 `canonical-json-v2` 或伪造值）时，硬拒绝还是降级？ |
| **推荐方案** | **硬拒绝，禁止静默回退**。注册期未知算法 → `ValueError`（注册失败）；读取期复算遇未知算法 → 错误码 `unsupported-digest-algorithm`，判定为不可验证而非"按当前算法重算" |
| 理由 | 静默回退会让 `scenario_digest` 的校验结论**不可信**：同一份内容在不同版本下算出不同摘要，却都被判"通过"，历史身份保障就失效了。Digest 的价值全在"同一算法同一结果"，一旦允许回退，等于把身份校验降级为"看起来像通过" |
| 历史算法处理 | **不迁移**。记录侧保存 `digest_algorithm` 与 `digest_algorithm_version` 两个字段，读取时按记录自带算法复算；算法不在白名单 → 拒绝，**不得改写历史记录去迎合新算法** |
| 实施阶段 | M1（与 Scenario 注册同期，属契约层） |
| 验收条件 | ① 未知算法注册被拒且有错误码；② 未知算法读取返回 `unsupported-digest-algorithm` 而非重算；③ 历史 v1 记录可读且结论不变；④ 用例覆盖"伪造算法名"与"跨版本读取"两类 |

### O2 Execution Lock 的作用域与崩溃恢复（R1：与 D4 解耦）

| 项 | 内容 |
|---|---|
| 问题 | 锁的跨进程范围、Worker 互斥、崩溃回收、fencing 是否需要 |
| **推荐方案** | **首期明确为单进程部署**：进程内 `run_id → 共享 Run 锁`，覆盖该进程内**全部 Worker**（Worker 是线程，不是进程）；同一 Run 的 `verify→execute` 区间由这把锁串行化。**多进程部署前必须补齐** DB Lease + fencing token + 启动扫描回收，否则不得扩容 |
| 理由 | 当前架构是单机单进程 + 线程 Worker（`apps/api/main.py:107` `max_workers`），进程内锁足以保证互斥。若首期就上 DB 锁，会把 M1 的复杂度推到分布式一致性上，而这一阶段的真实风险是"单机并发写同一 Run"，不是"跨机房" |
| 边界写法 | 把边界**写死在部署拓扑上**：文档明示"单进程；多进程 = 需要重新评审 O2"。这样锁的实现范围与部署形态一一对应，避免"代码是线程锁、部署却开了多副本"的默认错配 |
| 崩溃恢复 | **进程内锁无崩溃恢复问题**：进程崩溃 → 锁对象随进程消亡 → 新进程重新持锁。**不需要**心跳、**不需要**超时回收、**不需要** fencing。若将来引入跨进程锁，才需要 lease + fence，那属于 O2 的"多进程扩展"，须重新评审 |
| 实施阶段 | M1（单进程锁，随 M3-9 凭证机制落地）；多进程支持列为 M2 后独立评审项 |
| 验收条件 | ① 同一 `run_id` 并发两个 Action，验证者之一必须被阻塞（测试可证）；② Worker 数 >1 时仍满足互斥；③ 文档明确"多进程未支持"且服务在多副本配置下启动即拒或显式告警；④ 锁的行为**不受** D4 参数（数据租约心跳/超时）影响 |

#### O2 与 D4 的解耦（R1 核心修正）

首轮把崩溃恢复写成"用租约超时（**与 D4 参数联动**）"，并在验收条件里写"D4 参数变更能影响租约超时"。**这是错的，必须撤销**。两者的差异是本质的：

| 维度 | Execution Lock（O2） | 数据生命周期租约（D4） |
|---|---|---|
| 保护对象 | **同一 `run_id` 的 Action 串行性** | **测试数据的存活与清理权** |
| 作用域 | 单进程内存（线程间） | 跨 Run、跨进程可见的登记表（DB/文件） |
| 持有时长 | 毫秒～秒级（一个 Action 的 verify→execute 区间） | 整个 Run 生命周期（分钟级） |
| 失效方式 | 进程退出即失效（无残留） | 心跳超时才失效（有残留窗口） |
| 需要心跳吗 | **不需要** | **需要**（否则无法区分"活跃"与"崩溃"） |
| 需要 fencing 吗 | 首期**不需要** | 单进程首期不需要；多进程需要 |
| 参数归属 | 无参数（进程内锁的语义由代码决定） | 心跳间隔、超时倍数（D4 待批参数） |

**为什么必须解耦**——一个具体的错误推理链：

> "D4 批了心跳 10s / 超时 30s" → 若锁的恢复逻辑也读这两个值，则"把数据清理心跳调大以容忍慢 Run"这个**运维动作**，会**静默改变**执行锁的持有/失效行为。两个本该独立的机制被一根参数线牵住，任何一侧的调优都会以不可预期的方式影响另一侧。

**因此本节确立三条不可混淆的规则**：

1. **进程内锁不读 D4 参数**。`run_lock` 的实现中不得出现 `lease_heartbeat`、`lease_timeout`、`orphan_threshold` 这类名字。
2. **D4 参数只用于数据生命周期**（M1-4 清理器的孤儿判定）。它的语义是"多久没心跳算死"，与"一个 Action 是否正在执行"无关。
3. **多进程扩展不借用 D4 的参数**。若将来为执行锁引入 DB Lease，它的 lease 时长、续约间隔必须**单独评审、单独命名**，不得复用数据租约的配置键。

### O3 `url_and_content` 的归类与计数口径

| 项 | 内容 |
|---|---|
| 问题 | 当作 evaluator kind（+9，共 20 种，27 组），还是当作纯语法糖宏（+8，共 19 种，24 组） |
| **推荐方案** | **纯语法糖**：注册阶段展开为 `all_of`，**不进入 `SUPPORTED_KINDS`** |
| 理由 | 它的语义完全等价于"url 断言 ∧ content 断言"的合取，没有独立求值逻辑。把它放进 `SUPPORTED_KINDS` 会造成两处实现同一语义（宏展开 + kind 求值），长期必然分叉；而已有 `all_of` 能精确表达该语义，复用比新增更安全 |
| 需同步明确的三个数字 | ① **evaluator kind**：11 + 8 = **19 种**（`url_and_content` 不计入）；② **声明形式**：19 + 1 宏 = **20 种**（对外呈现不变，作者仍可写 `url_and_content`）；③ **参数化测试组**：**24 组**（原 27 组 − 3 组，宏展开的正确性由 `all_of` 组合测试覆盖） |
| 连带修正点 | 注册期 kind 合法性校验的判定集必须是 19 项；若校验集仍为 20 项，会出现"注册期接受、求值期无 handler"的空洞。验收矩阵 §3.1 / §3.2 / §6.1 三处数字须一并改 |
| 实施阶段 | M2（断言体系落地前定稿） |
| 验收条件 | ① `url_and_content` 不出现在 `SUPPORTED_KINDS`；② 注册期展开为 `all_of` 且展开结果可断言；③ 19 / 20 / 24 三个数字在设计与矩阵中一致；④ 参数化测试组数与矩阵声明数**逐一对齐**（不留"声明 24、实跑 26"这类漂移） |

### O4 Provider 默认模型绑定（R1：补实现级取证）

首轮只写"推荐三元组绑定"，读起来像一个待设计项。R1 读源码后发现：**现有实现已经踩中了要防的两个坑**，因此这项不是"设计选择"，而是"必须先修的错配"。

#### 现存实现（可复核）

```text
packages/agents/llm.py:280-283
    PROVIDER_ENV: dict[str, tuple[str, str]] = {
        "DEEPSEEK_API_KEY": ("deepseek", "https://api.deepseek.com/v1"),
        "OPENAI_API_KEY":   ("openai",   "https://api.openai.com/v1"),
    }

packages/agents/llm.py:286-300
    def provider_from_env(
        model: str = "deepseek-chat",          # ← 模型名默认值与 provider 无关
    ) -> tuple[LLMProvider, ModelConfig] | None:
        for env_name, (provider_name, base_url) in PROVIDER_ENV.items():
            key = os.environ.get(env_name)
            if key:
                provider = OpenAICompatibleProvider(base_url=base_url, api_key=key, model=model)
                return provider, ModelConfig(provider=provider_name, model=model)
        return None
```

#### 缺陷一：`OPENAI_API_KEY` 存在时会拿 DeepSeek 的模型名去请求 OpenAI

| 场景 | 实际发生 | 后果 |
|---|---|---|
| 只设 `OPENAI_API_KEY`，不传 `model` 参数 | `base_url=https://api.openai.com/v1` + `model="deepseek-chat"` | 请求必然 4xx（model 不存在）。更糟的是某些网关会把它**改写**成别的模型，于是成本台账与模型版本记录都失真 |
| 只设 `DEEPSEEK_API_KEY` | `base_url=api.deepseek.com` + `model="deepseek-chat"` | 恰好正确——**这正是缺陷被长期掩盖的原因**：主路径正确，另一条路径静默错 |

这是典型的"默认值绑定到了某一个 provider 的实现细节上"。`model` 的默认值属于 **Provider 三元组**的一部分，不能全局给一个。

#### 缺陷二：两个 Key 同时存在时**静默选择第一个**

`PROVIDER_ENV` 是 dict，Python 3.7+ 保证插入序，所以循环**恒先遇到 `DEEPSEEK_API_KEY`**。

| 场景 | 实际行为 | 风险 |
|---|---|---|
| 同时设置两个 Key | 无条件选 DeepSeek，**不报错、不告警、不记录** | 操作者以为在用 OpenAI（成本/合规可能只批了一家），实际跑在另一家；Trace 里 `provider` 字段会诚实地写 `deepseek`，但**没人会去看**，因为启动阶段没有任何提示 |
| 意图是"按配置选" | 无配置项可选 | 无法表达"这次用 OpenAI" |

`ensure_env_file_vars()`（`config.py:18-38`）会从 `.env` 注入变量，使得"两个 Key 都在 `.env` 里"成为**极易发生的默认状态**——而它恰好触发这个静默分支。

#### 缺陷三：三元组无校验、别名不受限

| 缺失的校验 | 现状 |
|---|---|
| `base_url` 与 `model` 是否同源 | 无校验（缺陷一的直接成因） |
| `provider` 与 `base_url` 是否匹配 | 由常量表保证，但一旦有人加第三个 Key 就失效 |
| `model` 是否为快照名（禁 `latest` 类别名） | 无校验，任意字符串直接透传 |
| `model` 是否在"已批准模型清单"内 | 无清单，无白名单 |

#### 推荐方案（维持首轮方向，但上升为"必须"）

| 项 | 内容 |
|---|---|
| **推荐方案** | 显式声明 **Provider → Endpoint → Model** 三元组绑定，并**拒绝跨 Provider 混搭**：`provider=deepseek` 只接受 `https://api.deepseek.com/v1` + `deepseek-*`；`provider=openai` 只接受 `https://api.openai.com/v1` + `gpt-*`/`o*`。三元组任一不匹配 → **启动期拒绝** |
| 双 Key 处理 | **必须显式选择**：新增 `LLM_PROVIDER` 配置项；未设置且检测到 ≥2 个 Key → **启动期拒绝并列出候选**，不得静默取第一个 |
| 模型名归属 | `model` 的默认值**随 provider 走**（`PROVIDER_ENV` 扩展为 `(provider, base_url, default_model)` 三元组），不再有全局默认 `deepseek-chat` |
| 理由 | 混搭的典型事故是"换了 Key 和 base_url，却继续用上一个 Provider 的模型名"。请求会以 4xx 或（更糟）被网关静默改写成另一个模型而"成功"，后者会污染成本台账与模型版本记录，使"记录实际返回的模型名"失去意义。启动期拒绝把这类事故前移到部署时 |
| 别名漂移 | 首期**禁止 alias 漂移**：配置写固定快照名，不使用 `latest`。若 Provider 侧强制漂移，则必须在 Trace 中记录**实际返回的模型名**（D8 已要求），二者取交集 |
| 实施阶段 | **M4 实施前完成**（配置校验代码可提前写，但**不得提前发起真实调用**）；缺陷一/二的修复本身不依赖 D8，可作为 M1 的独立小项 |
| 验收条件 | ① 三元组不匹配时启动失败并给出明确错误；② 两 Key 并存且未指定 provider 时启动失败；③ 只设 OpenAI Key 时不会出现 `deepseek-*` 模型名；④ 拒绝 `latest` 类别名；⑤ 运行时记录实际模型名；⑥ 上述逻辑全部用 **mock 单元测试**，**不发起真实网络请求** |

**四项的共同纪律**：O1～O4 的推荐方案**不改变任何既有决策、不代表任何实现、不解除 D8、不批准 D1～D5**。评审若采纳，需回写 §10 或对应设计章节，并在验收矩阵登记新准入项。

**R1 补充：N1 的暴露面判断有两个前提，缺一即失效**

| 前提 | 当前是否由系统强制 | 若失效的后果 |
|---|---|---|
| 监听地址是 loopback | **否**（默认值符合，但 `--host` 可变，且无校验） | 局域网/容器网络内任何人可访问全部审批接口 |
| 操作者可信 | **否**（无认证，仅靠物理/账号隔离） | 本机其他用户或进程可代签 |

因此"当前暴露面低"这个结论**不是系统保证的属性，而是使用者的自觉**。M1-0 的价值就在于把第一条从"自觉"变成"系统强制"；第二条在没有身份认证之前**无法**由系统提供，只能靠部署边界约束（单用户本机）来兜住。
