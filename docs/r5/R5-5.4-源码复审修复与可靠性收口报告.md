## 已修复

- **事务完整性。** 启动恢复在 Candidate 目录和事务目录取 Candidate ID 并集，持 Candidate 锁读取。发现含 `review_transaction_id` 的 Candidate 缺少日志即返回 409/BLOCKED，保留现存文件。空日志及损坏 JSON 保留原字节。无事务字段的历史 Candidate 仍可读取。
- **所有权与状态。** 在 Case 锁内核对当前 Candidate 与事务快照的 SHA-256、决策 ID、审核字段、正式资产中的所有权标记及其完整字节。已持久化 Candidate 阶段要求当前状态匹配 after，重复恢复按阶段前进。已能解析但存在冲突的事务沿用原设计持久化 BLOCKED 并记录原因。
- **运行时健康。** GET Candidate 的恢复失败在同一调用内记录 ID、状态和故障类型。`/health` 每次按持久化数据重新核验，发现缺日志、损坏及冲突即报告 degraded。该检查按本机数据量线性扫描，持锁时也可完成已有 durable intent。当前保证范围为单进程。
- **证据回读。** 字段路径显式编码键序列、字段集合或元素属性选择，复合观察保留原有整条观察路径。表单存在性用原始样本复核，属性读取与 evaluator 使用同一合并规则，transition 同时返回前后 URL，evidence_complete 同时返回来源引用与观察引用。每个子断言保留自己的观察、步骤、路径和引用；多步骤结果保留顺序。外部传入的 history 不参与单条观察的摘要。历史报告按其原字段路径及摘要精确复核。
- **编译契约说明。** 工作台解释负向路径的 PASSED 和业务目标 VERIFIED 门禁。编译器及审批 API 的 Oracle 准入保持原有实现。

### 自审发现及复验

1. 自审发现已持久化 Candidate 状态需要比对快照，并避免恢复时回写先前阶段。恢复现在按 SHA-256 比对前后快照，已替换的 Candidate 跳过重复写入。
2. 单独传入 history 曾影响无显式观察 ID 的回读。修复后单条观察独立求摘要，历史报告仍按既有引用校验。首轮 Mypy 发现的 page_state 键类型问题已修复。
3. 编译矩阵专项首次要求所有拒绝使用同一种错误详情，实际 project-query 的拒绝原因不同。专项固定两个独立 Oracle 各自的具体值。[原始失败](evidence/review-5.4/contract-audit.log)
4. Linux CI 在干净构建中发现负向路径提示丢失原有“未验证”文案，原本机 Python 全量先于 Vite 构建，未覆盖这处变化。恢复可读提示后先构建前端再执行原有浏览器断言和全部门禁。[Linux 失败原始日志](evidence/review-5.4/ci-4251489-pytest.log) · [重建后的专项日志](evidence/review-5.4/final-negative-ui.log)
