# R5-5.1 EventStore 持久化与 SSE 恢复设计

> 状态：已实施并经源码审查整改（R5-5.1 / R5-5.2 两轮实测；整改项见 §20）。§0–§19 为原设计，
> §7 已按实际代码重写为唯一正式游标协议；未闭合事项仍保留在 §19 与实施报告 §3.7，未删除。
> 基线：`r5-5-product-completion`（自 R5-4.10 HEAD `d78ec9c` 派生）
> 范围：只动 EventBus / SSE / 事件持久化 / 工作台事件与 Run 详情展示；**不动 C05 事件字段**

## 0. 要解决的问题

R5-4.10 交付的 EventBus 已经把「丢事件」变成可观测（`SubscriberQueue` 记账 + `: gap` 注释帧 + `eventaudit`），
但历史仍是一个进程内 `list`。因此：

| 现象 | 后果 |
|---|---|
| 服务重启后 `_history` 为空 | Run 详情页的事件流在重启后是空白，用户以为"没跑过" |
| `_sequence` 从 0 重新开始 | 新旧事件序号重叠，按序号做去重的客户端会误丢 |
| `Last-Event-ID` 查不到 | 旧行为静默回落 `after_seq=0`，全量重放（可能重复投递） |
| 无法区分"队列溢出丢的"与"重启丢的" | 缺口告警指向错误原因 |

## 1. 复用现有设施，不新建平行 EventStore

`packages/evidence/events.py` 已提供：`EventRow`、`EventStore`（append/query/by_id/mark_published）、
`Outbox`、`ConsumerInbox`、`ProducerInstance`、`detect_sequence_gaps`。它已经实现了本设计需要的三件事：

- 生产者侧幂等（`idempotency_key` 唯一约束 + 冲突审计）；
- 每生产者实例独立序号（`UniqueConstraint(producer_instance_id, sequence)`）；
- 受信 `workspace_id` 注入（`context_refs["workspace_id"]` 由服务端写入，绝不取 payload）。

本设计**只**在它之上补一件它没有的东西：**全局可排序的持久游标**。为此新增两张小表
（`ev_stream_cursor`、`ev_stream_state`），不新建第二个 EventStore，也不复制 append/幂等逻辑。

> 判定标准：任何"再写一个 append"的实现都违反第 1 条。所有写入必须走 `EventStore.append`。

## 2. RunEvent ↔ EventRow 字段映射

| RunEvent | EventRow | 说明 |
|---|---|---|
| `event_id` | `event_id` | 主键，SSE 的 `id:` 就是它（见 §7） |
| `event_type` | `event_type` | 原样 |
| `run_id` | `context_refs["run_id"]` | 不是独立列，避免改 C05/表结构 |
| `task_id` | `context_refs["task_id"]` | 同上 |
| `sequence` | `sequence` | 持久化开启时等于 `stream_seq`（见 §6） |
| `occurred_at` | `occurred_at` | 事件发生时刻 |
| `payload` | `payload` | 原样（JSON） |
| — | `observed_at` | 写入时刻，**不作为排序依据** |
| — | `producer_id` | 固定 `traceguard.eventbus` |
| — | `producer_instance_id` | 每进程一个（见 §3） |
| — | `workspace_id` | 受信上下文（见 §5） |
| — | `schema_version` | 沿用默认 `1.0.0-draft` |

`payload` 与 `context_refs` 均不改结构，因此 C05 消费方（`/events`、eventaudit、前端）无感。

## 3. `producer_instance_id` 如何确定

- 每个 **进程** 一个：`bus-<uuid4().hex[:12]>`，在 `EventBus` 构造时生成。
- 启动时调用 `EventStore.register_producer(instance_id, "traceguard.eventbus")` 登记到 `ev_producer_instance`。
- 语义与 C05 一致：重启 = 新实例 = 新序号空间，**旧序号永不复用**。
- 这也解释了为什么不能只靠 `sequence` 做跨重启游标：不同实例的 `sequence` 不可比。因此需要 §6 的全局位置。

## 4. `event_id` 如何保证幂等

同一 `event_id` 重复提交不得产生重复事件。实现方式：

1. `EventRow.event_id` 是主键 → 第二次插入必然冲突。
2. 幂等键默认 `f"{producer_instance_id}:{sequence}"`；`append` 前先按 `idempotency_key` 查询：
   - 命中且 payload/event_type 相同 → 返回已有行（重复投递，不新增）；
   - 命中但内容不同 → `ConflictError` + `ev_audit` 记 `IDEMPOTENCY_CONFLICT`。
3. 因为 `sequence` 由 `next_sequence()` 原子分配，同一实例内不会出现两个事件抢同一键。
4. 重新投递（outbox 重试、SSE 重放）走同一条路径，因此天然幂等。

回归要求：`append` 两次同 `event_id`/同键 → 库里仍只有 1 行，`ev_audit` 无冲突记录。

## 5. `workspace_id` 从受信上下文获得

- 唯一来源：`Settings`/部署上下文（当前默认 `ws-default`），由 `EventBus` 构造参数注入 `recorder`。
- **不接受** 事件 payload、HTTP 请求体、请求头里的 `workspace_id`。
- `EventStore.append` 会强制覆盖 `context_refs["workspace_id"]`（已有行为，本设计依赖它而不是复制它）。
- 测试：payload 里塞 `workspace_id="ws-evil"`，落库后必须是受信值。

## 6. 全局 sequence 与 producer sequence 如何兼容

这是本设计唯一的新增结构。

### 6.1 问题

- C05 要求「`sequence` 在 `(producer_instance_id, sequence)` 内唯一」→ 每实例从 1 开始。
- SSE 客户端要求「整个流单调递增」→ 需要跨实例的全局顺序。
- `observed_at` 是字符串时间戳，同毫秒内并列、时钟回拨都会破坏顺序 → **不能作为唯一排序依据**。

### 6.2 方案：持久游标表

```text
ev_stream_cursor(stream_seq INTEGER PRIMARY KEY AUTOINCREMENT,
                 event_id   TEXT UNIQUE NOT NULL)

ev_stream_state(id INTEGER PRIMARY KEY,          -- 恒为 1
                pruned_through INTEGER NOT NULL) -- 保留窗口水位
```

- 每次 `append` 在**同一事务**内写 `EventRow` 与 `ev_stream_cursor`，`stream_seq` 由数据库分配，
  因此顺序是数据库权威的，不依赖时钟。
- `EventBus.publish` 在持久化开启时把 `sequence` 设为 `stream_seq`：全局单调、跨重启连续。
  `(producer_instance_id, sequence)` 仍唯一，因为每个进程的实例 ID 不同。
- 持久化关闭（内存模式）时 `sequence` 仍是原来的进程内计数器，行为不变。

### 6.3 兼容性

- 旧数据库没有这两张表：`create_event_tables()` 用 `create_all(checkfirst=True)` 自动补建（新表，不 ALTER 旧表）。
- 旧事件没有 `ev_stream_cursor` 行：`replay` 以 `stream_seq` 排序，缺行事件**不会**被回放；
  因此启动时执行一次 `backfill_stream_cursors()`（按 `(observed_at, sequence)` 顺序补齐游标行），
  只在存在无游标事件时执行。这一步是**迁移**，写入日志与计数，绝不静默。

## 7. 唯一正式 SSE 游标协议（Last-Event-ID）

> 本节是**唯一权威定义**。源码审查发现旧文稿写的是 `id: <event_id>` 且把 v2 记成 4 段，
> 与实际发送的 `v2:<stream_seq>:<producer_instance_id>` 不符——以本节和代码为准。

### 7.1 先分清两个概念（不得再假设二者相等）

| 概念 | 载体 | 谁分配 | 含义 | 能否作为恢复游标 |
|---|---|---|---|---|
| **事件身份 / 投递顺序** | `event_id`（`runevt_<hex>`）+ `delivery_seq`（进程内投递序） | 发布进程 | "这是哪一条、在本进程线上排第几"，含未落库事件 | 否（身份≠恢复点） |
| **已确认持久化的恢复游标** | `v2:<stream_seq>:<producer_instance_id>` | SQLite（`ev_stream_cursor`） | "数据库已确认写到第几条，可从这里之后续接" | 是 |

两者在持久写入成功时数值相关，但**从不共享同一域**：`delivery_seq` 每条都加，包括写库失败的事件；
`stream_seq` 只有真正落库才产生。写库失败期间发过的事件绝不能拿到一个"看起来有效"的持久号段，
否则数据库恢复后写入的新事件会复用该号，客户端重连时会把它当成"已见过"而静默跳过。

### 7.2 发送端（`id:` 行）唯一规则

| 模式 | 事件状态 | SSE `id:` | 依据 |
|---|---|---|---|
| 持久化（有 recorder） | 写入成功，`sequence` 非空 | `v2:<stream_seq>:<producer_instance_id>`（**3 段**） | `RunEventRecorder.cursor_token()` |
| 持久化 | 写入失败（degrade），`sequence` 为 `None` | **不发 `id:` 行** | `EventBus.cursor_token()` 返回 `None`，`_sse()` 省略 id 行 |
| 内存（无 recorder） | 任意 | `id: <event_id>`（旧行为不变） | `EventBus.cursor_token()` 回退 event_id |

- 浏览器收到无 `id:` 的帧时保留上一次的 `Last-Event-ID`（SSE 规范行为），因此重连从**最后一个可证明的持久点**续接，
  而不是从"已送达但未落库"的假点续接。
- 无 id 的事件仍在 `data:` 里明确标记 `durable:false`、`sequence:null`、`delivery_seq:<n>`，
  前端按 `event_id` 去重（**不按序号**），所以恢复后的真实事件不会被序号去重吞掉。

### 7.3 接收端（`Last-Event-ID`）解析顺序与判定

`RunEventRecorder.resolve()` 按以下顺序校验，首个失败即返回，伪造游标无法借合法位置背书：

1. **格式**：必须严格匹配 `v2:<非负整数>:<非空实例>`；`+1`/` 1`/空段均视为 `malformed`。
2. **实例归属**：`producer_instance_id` 必须在本库 `ev_producer_instance` 注册过 → 否则 `cursor-unknown`，
   reason=`unknown-instance`（这就是"跨库位置相同"被拒绝的原因）。
3. **保留水位**：`stream_seq <= pruned_through` → `cursor-expired`，从最早保留事件全量回放。
4. **越界**：`stream_seq > latest` → `cursor-unknown`，reason=`beyond-latest`，不回放、从末尾续推。
5. **位置-实例绑定**：该位置事件的 `producer_instance_id` 必须与游标声明一致 → 否则 `owner-mismatch`。
6. **存在性**：该位置必须真有保留的事件 → 否则 `position-gap`。
7. 全部通过 → `ok`，从该位置之后回放。

**合法历史实例**（已注册、但不是当前进程实例）必须接受：`Last-Event-ID` 通常跨重启到达，
若要求等于当前进程实例，每次重启都会静默从头开始。当前进程只校验"本库注册过 + 位置属于声明实例"。

### 7.4 旧 `event_id` 兼容

- `runevt_xxx`（旧格式）仍接受：查 `ev_stream_cursor` 得到 `stream_seq`，随后走同一保留水位判定。
- 行已被裁剪 → `cursor-unknown`，reason=`legacy-not-found`，带 `pruned_through` 让运维区分"服务端忘了"与"客户端发垃圾"。
- 新旧客户端可混用；旧客户端忽略 `stream.notice`，只看 `id:`/`data:`，行为不回退。

### 7.5 传输层提示帧（`stream.notice`，非 C05 事件）

| code | 触发 | 客户端动作 |
|---|---|---|
| `cursor-unknown` | 格式错 / 实例未注册 / 越界 / 位置空隙 / 绑定不符 / 旧 id 未找到 | 显式重建或放弃历史，不静默全量重放 |
| `cursor-expired` | 位置低于保留水位 | 回放全部保留事件，并告知缺口 |
| `persist-degraded` | 本轮出现写库失败且尚未恢复 | 标记流"不可回溯"；看 `/events/durability` 的 `mode`/`recovered`/`undurable_*` |
| `gap` | 订阅队列溢出 | 按注释帧 `: gap` 的区间续接 |

`reason` 为稳定机器子码（`malformed`/`unknown-instance`/`below-watermark`/`beyond-latest`/
`owner-mismatch`/`position-gap`/`legacy-not-found`），运维无需解析英文 detail。

### 7.6 重启后的续接规则

- 新进程以新的 `producer_instance_id` 注册；**历史实例游标仍有效**（§7.3.7），从游标位置续接。
- `persistence_snapshot().mode` 是当前能力（`degraded` 仅在失败未恢复时），`failures`/`undurable_*` 保留历史缺口；
  `recovered:true` 表示已恢复到 `durable`。恢复不伪造历史补写（无回填失败期间的事件）。
- strict 策略下写库失败直接抛出（不产生 wire 事件、不推进 `delivery_seq`）；degrade 策略按 §7.2/§7.5 处理。

## 8. 服务重启后的回放

```text
client: Last-Event-ID = v2:42:producer-instance-A   # 或旧格式 runevt_abc
server: resolve -> 格式/实例/水位/越界/绑定/存在性 全部通过 -> after=42
        replay(after=42, limit=N)  -- 从 ev_event 按 stream_seq 升序
        -> 逐条 SSE 发送（id 为 v2:<位置>:<该事件的生产实例>，见 §7.2）
        -> 追平后进入 live 轮询
```

- `EventBus.__init__(recorder=...)` 时以 `recorder.latest()` 初始化**持久高水位**；
  投递序号 `delivery_seq` 从 0 独立开始，新事件的位置由数据库分配，不会与重启前的序号冲突。
- `_history` 仍然保留（同进程内快速重放、`subscriber_stats` 诊断），但**不再是唯一来源**。
- 内存历史加封顶（`_MAX_MEMORY_HISTORY`），避免长稳期间无界增长；持久化层才是权威。

## 9. 历史保留窗口

- 保留策略按条数：`retention_events`（默认 20000，可配置）。
- 触发点：启动时 + 每 `prune_interval`（默认 500）次 append。
- 删除：`stream_seq <= cutoff` 的 `ev_event` 行 + 对应 `ev_stream_cursor` 行，并把 `pruned_through = cutoff`。
- **不删除** `ev_producer_instance` / `ev_audit`（审计与实例空间是历史事实）。
- 保留窗口与 Run 运行状态无关：删除的是"很久以前的事件副本"，Run 行、证据、图节点不受影响。
  报告必须写清这一点，避免被理解为"删了业务数据"。

## 10. 过期游标处理

- 判定：`cursor.stream_seq < pruned_through` → **cursor-expired**。
- 行为：回放**全部保留事件**（从最小 `stream_seq` 开始），并先发一条控制帧：

```text
event: stream.notice
data: {"code":"cursor-expired","requested":"runevt_abc","requested_sequence":12,
       "oldest_retained":8601,"latest":9120,"detail":"..."}
```

- 不静默：客户端至少能看到"你要的那段已被裁剪"。
- 不发 `: gap` 注释帧来表达过期：注释帧语义是"序号缺口"，与"保留窗口裁剪"是两件事（见 §12）。

## 11. 未知游标处理

- 判定：格式不认识（既不是 `v2:` 也不是已知 `runevt_`），或 event_id 在游标表中查不到且不是保留窗口内的缺口。
- 行为（**改变旧行为**）：**不做全量重放**。从 `latest_stream_seq` 开始只推新事件，并先发：

```text
event: stream.notice
data: {"code":"cursor-unknown","requested":"...","latest":9120,
       "detail":"cursor not found; history not replayed to avoid duplicate delivery"}
```

理由：全量重放会把客户端已经处理过的事件再发一遍，而客户端无从判断；"丢弃历史 + 明确告知"
比"静默重复"更可控，客户端需要历史时可以显式调 `GET /events?after_sequence=` 重建。
这与旧行为的差异会写进报告与 README，属于**行为变更**，必须显式登记。

## 12. SSE gap 与持久化缺口如何区分

| 来源 | 含义 | 信号 | 客户端应对 |
|---|---|---|---|
| `SubscriberQueue` 溢出 | 这条连接消费太慢，队列丢了这个连接的事件 | `: gap from=.. to=.. dropped=N`（既有注释帧，保留）+ `stream.notice{code:"gap"}` | 继续用游标续接 |
| 保留窗口裁剪 | 服务端已不再保存那么早的历史 | `stream.notice{code:"cursor-expired"}` | 全量重建 |
| 游标不可识别 | 客户端给的 id 服务端不认识 | `stream.notice{code:"cursor-unknown"}` | 显式重建或放弃历史 |
| 持久化写入失败 | 事件已实时投递但**没有**落库 | `stream.notice{code:"persist-degraded"}` + `/events/durability` | 知道"这条流不可回溯" |

四者语义不同，不能合并成同一个提示。注释帧保持兼容（旧客户端忽略），新客户端读 `stream.notice`。
`stream.notice` 是**传输层控制事件**，不是 `RunEvent`，因此 C05 字段零改动。

## 13. EventBus 与 EventStore 的失败处理

写入失败时**绝不伪造成功**。两种策略，由构造参数 `persistence_failure_policy` 决定：

- `degrade`（API 默认）：实时投递照常，但该事件被标记为**不可持久**；
  `EventBus.durability_state()` 返回 `{mode, degraded, failures, last_error, first_undurable_sequence}`；
  SSE 在状态变化时发 `persist-degraded`；`/events/durability` 可查。恢复后**不回填**——
  没落库就是没落库，事后补写会让"可追溯"变成谎言。
- `strict`（门禁用/测试用）：`publish` 直接抛 `EventPersistenceError`，调用方看到真实失败。

无论哪种策略，日志都带 `event_id`/`event_type`/`run_id` 与异常类型，便于定位。

## 14. 数据库不可用时是否允许继续执行

**允许**（决策 D-R5-511-2）。理由：

- 事件持久化是可观测性基础设施，让"测试执行"因为"日志写不进去"而失败，会把一个观测故障升级成产品故障；
- 但必须让退化**可见**：`/health` 保持只查 DB 连通性，`/events/durability` 单独报告事件层状态，
  前端常驻"事件未持久化"横幅；
- 若 DB 完全不可用，`EventStore.append` 会快速失败（不会长时间阻塞 worker），
  因为 `degrade` 模式下异常被捕获并计数，不重试、不排队。

## 15. 多客户端并发回放

- 每个 SSE 连接独立 `SubscriberQueue`（既有设计），回放用各自游标，互不串线。
- 回放是**只读查询**，不占写锁；`LIMIT` 分批（默认 500/批），避免一次性把 2 万条读进内存。
- 慢客户端只影响自己（既有 `note_drop` 记账），不影响其他连接与 worker。
- 测试：4 个连接不同 `Last-Event-ID` 同时回放，各自收到的序列集合互不污染。

## 16. 历史迁移与兼容性

| 场景 | 处理 |
|---|---|
| 旧库无 `ev_stream_cursor` / `ev_stream_state` | `create_all` 补表；启动时 `backfill_stream_cursors()` 补行并记录计数 |
| 旧 `Last-Event-ID`（event_id） | 支持（§7） |
| 内存模式（无 recorder） | 完全保持 R5-4.10 行为，所有既有测试必须继续通过 |
| C05 schema | **不改**。`stream.notice` 是 SSE 传输帧，不是 Event |
| 前端 | 新增监听 `stream.notice`；未升级的客户端忽略未知 `event:` 类型，不报错 |

## 17. 测试矩阵（必须真实数据库 + 真实 HTTP SSE）

## 18. 工作台前端

- 事件流面板顶部状态条：`连接中 / 实时 / 重连中（第 n 次） / 已断开`；
- 恢复状态：`已从游标恢复 N 条 / 首次连接（无游标）`；
- 提示条（可关闭，按 code 分色）：`历史缺口 gap` / `cursor-expired` / `cursor-unknown` / `persist-degraded`；
- Run 详情：业务 `Verdict` 与 `CleanupStatus` 分两块展示，清理失败用"资源"语义，不染红业务结论；
- 具体失败细分：浏览器关闭失败 / Trace 停止失败 / Evidence 采集失败 各自独立一行，来自
  `RunReport.cleanup`（C04）。

## 19. 已知限制（必须写进报告）

1. SQLite 单写者：高并发写入会串行化；本设计不引入外部 broker（未批准）。
2. `stream_seq` 由 SQLite `AUTOINCREMENT` 分配，跨库/跨部署不做全局唯一承诺。
3. `degrade` 模式下，写入失败期间的事件不可回溯，这是设计选择而非缺陷。
4. 保留窗口按条数而非按时间，长跑高事件量场景需要调参。
5. `cursor-unknown` 不再全量重放是**行为变更**，旧前端需要配合（本设计同步更新前端）。

## 20. 源码审查整改（R5-5.1 / R5-5.2，本轮）

> 本节记录正式源码审查后的缺陷整改，不扩张功能；逐项根因与证据见实施报告 §6。

### 20.1 P0-2：投递序号与持久游标分离

- **根因**：旧 `EventBus._next_sequence()` 写库成功用 `stream_seq`、失败用本地 `_sequence`，两者共处一个号段。
  失败期间的 wire 号随后被数据库恢复后写入的新事件复用；客户端按序号去重会静默跳过真实事件。
- **修改**：`RunEvent` 拆出 `sequence: int | None`（持久位置，非空才有号）与 `delivery_seq: int`（进程投递序，
  每条都推进）。`cursor_token()` 对未持久化事件返回 `None`，`_sse()` 因此**不发 `id:` 行**；
  `data:` 以 `durable:false`/`sequence:null` 明确标记。前端改为按 `event_id` 去重，不按序号。
- **验证**：真实 SQLite + 真实 HTTP SSE 的故障注入测试 `tests/test_sequence_faults.py`，
  覆盖"100 条正常 → 故障期 2 条 → 恢复 → 再 3 条 → 重连"，strict/degrade 分别验证，无重复投递、无静默丢失。

### 20.2 P1-1：v2 游标身份校验

- **根因**：旧 `resolve()` 只解析 `stream_seq`，不验证 `producer_instance_id`；跨库位置相同即被误判为有效。
- **修改**：`resolve()` 按 §7.3 的 7 步校验；`CursorResolution.reason` 给出稳定子码。
  合法历史实例仍接受，不要求等于当前进程实例。新增 Store 原语
  `knows_producer_instance()` / `position_owner()` / `stream_position(instance)`。
- **验证**：`tests/test_cursor_identity.py`（同库历史实例 / 未知实例 / 跨库同位 / 越界 / 已裁剪 /
  畸形 / 非法实例+合法位置）与 `tests/test_event_persistence.py` 的游标矩阵。

### 20.3 契约边界

C05 字段零改动（`sequence` 保持可选数字，`durable`/`delivery_seq` 随 payload 传递但注册表 schema 不扩字段）。
新增的 `stream.notice` 是传输层控制事件，不是 `RunEvent`。`first_undurable_sequence` 保留为**投递序号**的
弃用别名，供旧消费者读取，含义已在 `persistence_snapshot()` 注释中写死。

### 20.4 仍未闭合（未删除，转入 P2 独立计划）

- 30 分钟长稳、大量事件写入下的保留窗口裁剪压力验证、多客户端并发回放、服务重启组合场景：
  转入独立测试计划（见实施报告 §7），本轮不作为阻塞项。
