## 3. 问题 C：SSE 生命周期（最严重，影响产品可用性）

### 3.1 复现（`.traceguard-tmp/r5/r549/repro_sse.py`）

```text
run: run_20261124051332073755_aeeb66
status: 200 text/event-stream
apps/api/workbench.py:137: RuntimeWarning: coroutine 'Request.is_disconnected' was never awaited
elapsed: 0.03s raw_lines=4 data_frames=1
persisted events: 2
```

流在 0.03 s 内结束，只吐出回放的那 1 帧——`run.running` / `run.finished` 等实时事件**永远不会送达**。
原因：`generate()` 是**同步生成器**，却调用协程 `request.is_disconnected()`；协程对象恒为真值，`if` 立即成立 → `break`。

### 3.2 修复（`apps/api/workbench.py`）

1. 改为 `async def generate()` + `await request.is_disconnected()`；
2. 队列消费从阻塞 `q.get(timeout=1.0)` 改为 `get_nowait()` + `await asyncio.sleep(0.2)`，不占用事件循环、断连可及时响应；
3. keep-alive 由"每 15 次空轮询"改为**按空闲时长**（15 s）触发，不再与轮询频率耦合；
4. **订阅移入生成器内部**：连接在响应体开始迭代前就断开时，Starlette 不会运行生成器，原先 `subscribe()` 注册的队列永久泄漏（实测复现）；
5. 回放与实时用 `last_seq` 去重，同一连接内不出现重复 `event_id`（Last-Event-ID 语义依赖它）。

### 3.3 回归（`tests/test_sse_lifecycle.py`，6 项，真实 uvicorn + 真实 HTTP 流）

| 测试 | 断言 |
| --- | --- |
| `test_live_events_after_connect_are_pushed` | 订阅后发布的 3 个事件按序到达（旧代码此测试必失败） |
| `test_real_execution_events_reach_the_stream` | 真实运行产生 `run.queued → run.running → run.finished`，终态为最后一帧 |
| `test_last_event_id_replays_only_later_events` | 带 `Last-Event-ID` 只回放游标之后，无重复 |
| `test_multiple_clients_each_receive_the_same_event` | 两个客户端收到同一个 `event_id`（fan-out） |

## 4. 问题 A：截图 Protocol Error

### 4.1 根因（两条，均为真实缺陷）

1. **取证失败被记成业务失败**：`_capture_screenshot` 直接 `page.screenshot()`，异常冒泡到 `execute_step` 的兜底 `except` → 已经成功的业务动作被判为 `ok=False`，进而进入 Oracle 观测 `ui.<step>.passed=False`，产出**虚假业务 FAILED**。
2. **CI 容器 `/dev/shm` 只有 64 MB**：Playwright 对 chromium **不会**自动加 `--disable-dev-shm-usage`（实测：该参数只出现在 electron 的默认参数里）。无头 Chrome 渲染 + 截图时 renderer 被 OOM kill，表现正是 `Page.screenshot: Protocol error`。

### 4.2 修复

- 新增 `launch_args()`（`packages/execution/browser.py`），Explorer / 正式执行 / 两个验收脚本**共用同一份启动参数**，加 `--disable-dev-shm-usage`（Windows/macOS 无副作用）；
- `page.on("crash")` 监听 + `page_crashed` / `crash_detail` 状态；
- 截图与 DOM 取证失败 → 记 `evidence.screenshot.failed` / `evidence.dom.failed` 事件并返回空 id，**不再让步骤失败**（取证缺口与业务结论分离）；
- 步骤执行前检查页面可用性；页面已消失时返回 `StepExecution(blocked=...)`，并只发 `step.blocked` 事件；
- runner 对 `blocked` 步骤**不发布任何观测**（"没观测到" ≠ "观测为假"），并把 `page_crashed` 反映为 `execution_status=FAILED` + `run.browser_crashed` 事件；
- 浏览器关闭失败不再吞掉异常，记 `browser.close.failed`。

### 8.1 安全专项的 1 项环境性失败（如实记录，门禁记 FAIL）

> **R5-4.10 更正**：本节初版把该结果写作"BLOCKED（环境）/ 不计入 PASS"。
> 复核 `security-final2/report.md` 与 `report.json`，门禁**实际记录的是 `FAIL`（exit=1）**，
> 因为 verify_all 的 BLOCKED 判定只接受"缺模块 / 缺浏览器 / 端口被占"三类窄签名，
> 而本条是测试自身的断言失败，不匹配任何签名。把 FAIL 描述成 BLOCKED 会低估失败，
> 因此此处更正为 FAIL。判定逻辑本身是正确的，本轮不因此放宽签名（详见 R5-4.10 §3.1）。

`tests/test_repair_sandbox.py::test_target_startup_failure_is_reported_not_promoted` 失败，
栈内证据为该测试自身的断言 + 宿主守卫日志：

```text
SandboxResult(..., cleanup_error='cleanup blocked: SystemExit')
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50,"scope":"turn", ...}
assert not (SANDBOX_ROOT / result.sandbox_id).exists()   # 目录确实还在，因为删除被守卫拒绝
```

- 产品行为是**正确且诚实**的：清理被拒 → 记录 `cleanup_error`，不谎报已清理；
- 单独运行该文件 **5 passed**，且**同一测试在两次全量门禁（484 passed）中均通过** —— 差异只取决于同一进程内此前累计删除的次数（安全门禁把 `test_sandbox_paths` 排在它之前，先耗尽了阈值）；
- 归因：本机代理环境的批量删除守卫（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，`scope=turn`）。GitHub Actions 环境是否同样触发**未验证**——本仓库 CI 尚未在该分支实际运行过；
- 结论：门禁**记 FAIL**（92 passed / 1 failed），不计入 PASS，也不冒充 BLOCKED；已记为遗留改进项（见 §9.6）。

### 8.2 本轮顺带发现并修掉的验收脚本缺陷（非产品缺陷，但会让门禁说谎）

1. `scripts/e2e_product_flow.py` 未把仓库根加入 `sys.path`，新增的 `launch_args` import 触发
   `ModuleNotFoundError: No module named 'packages'`，使 `workbench-ui-loads` 失败（23/24）。
   修法与 `ui_acceptance.py` 对齐：脚本顶部 `sys.path.insert(0, ROOT)`。修复后 **24/24**。
2. `scripts/ui_acceptance.py` 的深链检查用固定 `wait_for_timeout(900/1000 ms)` 等待诊断渲染，
   而诊断接口在 15 条证据上实测 **≈2.06 s**（三次调用 2067/2065/2058 ms），必然超时 → 4 项深链断言稳定失败。
   改为 `wait_for_selector(".meta", timeout=20 s)` 的确定性等待后 **150/150**。
   这是"用 sleep 当同步原语"的典型缺陷，不是放宽标准：元素 20 s 内不出现仍然记 FAIL。

## 9. 已知限制

1. SSE 订阅队列上限 1000；极慢消费者会丢事件且**本轮无 gap 信号**（重连后靠 `Last-Event-ID` 补齐）。已在 `EventBus.publish` 注释中记录。
   → **R5-4.10 已处理**：新增按订阅者记账 + SSE 注释帧 `: gap from=.. to=..`，缺口可检测且不改 C05 事件字段；SSE 历史仍是进程内 `list`，重启即失效（详见 R5-4.10 §3.3 / §3.4）。
2. SSE 轮询间隔 0.2 s，即事件推送延迟上限 ≈ 200 ms；未改为 asyncio 队列，因为发布方在工作线程中，改造面大于收益。
3. `StepReport` 属于 C05 生成契约，本轮**未加字段**，blocked 用 `detail` 前缀 `BLOCKED:` 表达；如需一等字段，须走契约评审。
4. 截图 Protocol Error 的 CI 复现依赖 Linux 容器 `/dev/shm` 条件，本机（Windows）无法 1:1 复现；本机验证的是"崩溃/取证失败的处理路径"。启动参数（`--disable-dev-shm-usage`）是针对该根因的缓解，**尚未在 GitHub Actions 上实际验证过**。
5. 长稳（30 min）与恢复演练未在本轮重跑 —— 本轮改动不触及存储、调度与迁移路径；上一轮 R5-7 复核数据仍然有效（详见 `docs/r5/R5-7-系统级验收复核报告-R5-4.md`）。
6. `RepairSandbox` 仍使用固定根目录 `.traceguard-tmp/r3`，测试之间会累积子目录（历史上曾达 107 个），是本机批量删除守卫被触发的直接原因。建议后续为其增加可注入 `root`，让测试落到各自 `tmp_path`（涉及安全路径包含性检查，需单独评审）。
7. 诊断接口对 15 条证据耗时约 2 s，页面在此期间只有 loading 态；本轮未做性能优化（无证据表明是瓶颈），已记入观察项。
