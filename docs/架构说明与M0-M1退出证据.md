## 1. 为什么先做这个

v1.1 的设计文档（11 份）+ 路线图（14 阶段）+ R1 调研（32 份）已完成，但全项目 0 行代码。本骨架把重心从"继续精炼文档"切换到"跑通第一个可运行实体"，对齐路线图 M0/M1 的退出目标。

## 2. 关键架构决策（含理由）

| 决策 | 选择 | 理由 |
|---|---|---|
| 数据访问层 | SQLAlchemy 2.0，默认 SQLite，可切 PostgreSQL | 路线图阶段 0 要求"可复现可启动"；本机 Docker daemon 未启动。方言中立使 DATABASE_URL 一切即可切 PG，不违背 v1.1 生产目标 |
| Ground Truth 隔离 | 独立表 + 独立 `/__eval__` 路由 + token 校验 | 阶段 1 明确"Ground Truth 不暴露给 Agent"。分表使业务查询不可能误读到答案；token 使 Agent 拿不到 |
| 业务状态权威 | 独立状态查询 API 直读 `tf_project` | 阶段 1 明确"独立业务状态查询，不能只依赖 UI 证明业务成功"。UI 可被 TF-UI-001 欺骗，DB 行不会 |
| 故障注入 | 可开关的 FaultConfig + EventLog | 五类故障需"可注入、可清理、可重复"；EventLog 提供故障确实触发的证据（非阶段 4 的防篡改 Evidence） |
| 演示认证 | 明文测试账户 | 阶段 1 允许最小实现；已在代码与配置中显式标注 prod 必须改 hash + 强 token，并在 `validate_for_prod()` 中 fail-fast |
| 契约目录 | 仅注册表 + C12 示例 | 项目资料/05 明确"正式字段和 JSON Schema 待逐项冻结"，禁止编造冻结契约 |

## 5. 测试中发现并修复的缺陷（过程证据）

1. 外键顺序：TestUser 无 ORM relationship，插入早于 Workspace → FK 失败。修复：seed 后 flush 父行。
2. 依赖类型：eval/api 依赖函数 `request` 未标注类型 → FastAPI 误判为必填 query 参数（422）。修复：标注 `Request`。
3. 故障真值陷阱：`TF-DB-001` 空参数 `{}` 被 `if db_fault` 当作假 → 故障未触发。修复：改 `is not None`。
4. 缺失导入：service 抛 `DomainError` 但只导入子类。修复：补导入。
5. 内存 SQLite：多连接各自独立 → 建表不可见。修复：StaticPool。

这些缺陷通过"边写边测"发现，说明 M0 的 CI/测试基建本身就是质量保证的一部分，而非事后补充。
